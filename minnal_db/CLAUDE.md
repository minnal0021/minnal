# minnal_db — KV Engine

WiscKey-style embedded store: keys live in an LSM tree, values in a separate value log, reducing write amplification for large values.

> **This file covers the KV engine (`src/db`, `src/store`, `src/support`).** `minnal_db` is a single feature-gated crate that also folds in `src/index/` (field indexing, always on), `src/semantic_search/` + `src/vector_kv.rs` (`#[cfg(semantic-search)]`), and `src/doc_store/` (`#[cfg(doc-store)]`). See the root `CLAUDE.md` for the feature model and the folded modules' own `CLAUDE.md` files.

**The index checkpoint interval is the crash-replay window.** `scheduled_tasks.index_checkpoint_interval_ms` (default **1750 ms**) sets how often every field index is made durable, and after a crash each field replays the WAL from its last checkpoint. It was hardcoded at 15 minutes, which meant a crash could face fifteen minutes of writes to replay — measured at 7–27 minutes to restart a 16k-document store. It also caps WAL retention, since the index-replay watermark holds segments until a checkpoint advances. The per-tick cost is a flush per field index plus one marker write (tmp + rename + two fsyncs) per field.

**WAL replay batches by value — keep it.** `activate_field_index` resolves every affected key first, groups the rows by extracted value, clears them all with `remove_all_for_rows` (one membership probe per bucket for the whole set), then changes each value's bitmap once with `insert_many`. It was introduced when every index write appended a whole bitmap, so the per-key form left one dead copy *per key* (a 6,000-key replay went 626 ms → 104 ms). Field-index writes now go to an in-memory overlay and are written once per spill, so the overlay would coalesce a per-key loop anyway; the grouping still saves a slot lookup and a bucket probe per key. Replay is bounded by the database's shared overlay budget (set on the field before replay; the hard limit spills mid-replay) and compacts inline on the `index_blob_backpressure_bytes` cap — the default cap when that is 0 — because the checkpoint worker is not running yet. ## Data flow (write path)

```
Db::put(key, value)
  → Database::put
      → key stripe lock (outermost — see below)
      → WAL append under the WAL lock (seq, frame), lock released
      → commit round: wait until an fsync covers the entry (group commit)
      → Value log write → pointer
      → Memtable insert with pointer (best-effort w/ bounded retry; ERROR-logged
          if all retries fail — data IS durable in WAL and replayed on next startup)
      → When memtable hits threshold → flush to SSTable
      → Background: LSM compaction, value-log GC, WAL GC, TTL cleanup
```

`Db::merge(key, operand, closure)` is the one read-modify-write: it reads the key,
runs the caller's closure over `(existing, operand)`, and writes the result back
under the same key stripe, so no other write to that key can land in between. The
WAL sees only the *result* — an ordinary `Upsert` or `Delete` tagged
`op_name: "merge"` — so recovery, WAL GC and index replay are untouched and
nothing re-runs the closure at replay (a closure cannot be serialised, and
recovery runs long before user code could re-register one).

Every write is a single-op WAL transaction — there is no batch/transaction primitive. The in-memory apply is best-effort with bounded retry (`Database::apply_with_retry`): once a WAL fsync covers the entry the op is durable and the call returns `Ok` regardless of the apply outcome. Recovery **replays every entry at or above its namespace's saved safe offset (`WalMetadata::replay_from`) in global sequence order** (so writes to the same key resolve to the last writer), retries each once, and writes persistent failures to `fail_logs/<timestamp>.json`.

## Concurrency & correctness invariants

These are load-bearing; preserve them when touching the store/GC paths:

- **The key stripe is the OUTERMOST write lock.** Every WAL-backed write and both
  no-WAL writes take `Database::key_locks.guard(ns_id, key)` before anything else,
  giving one uniform order: **`key stripe → wal_metadata → (released) → value-log
  bucket`**. Nothing else in the crate takes a stripe, which is what makes a cycle
  impossible rather than merely unlikely — so do not introduce a path that acquires
  a stripe while holding either of the other two. It exists for `merge_ns`, which
  must read a key and write it back indivisibly: `wal_metadata` is global (running
  a user closure under it would stall every namespace) and the bucket lock is taken
  only *after* the WAL lock is released, so serialising on it would invert the
  established order. Cost on `put`/`delete` is an uncontended mutex: each holds
  its stripe across its append and its commit-round wait anyway. TTL expiry takes it too
  (`KVStore::expire_records_locked`, handed `key_locks.guard` by `run_ttl_pass`),
  and deletes by compare-and-set: only if the key still points at the record it
  judged expired, with its seq allocated after that check. Before, TTL sat outside
  the stripe, allocated its seq before the bucket lock and deleted whatever the key
  held — so it could delete a value written during the pass, and it was the one
  source of out-of-order seqs (a delete older than a put applied after it, or the
  reverse), which in turn made losing writes corrupt the field index (see *losing
  writes* below). Regression test:
  `test_expiry_spares_a_value_rewritten_after_it_was_judged_expired`. GC's re-point
  alone sits outside the stripe, deliberately (sequence-preserving, so it creates no
  new version). Stripes are
  hashed from the **whole** key, not `get_bucket_for_key`'s 8-byte prefix — reusing
  that would collapse every key sharing a prefix onto one stripe. Regression tests:
  `concurrent_merges_on_one_key_lose_no_updates`,
  `a_blind_put_cannot_land_in_the_middle_of_a_merge` (both fail if the stripe is
  removed), `writers_and_gc_make_progress_together`.
- **Sequence == WAL order, and the memtable resolves conflicts by it.** Writers allocate the global sequence (`Database::next_seq`, shared into every `KVStore` via `set_seq_counter`) *inside* the WAL append lock, so on-disk WAL order == sequence order. The memtable resolves same-key conflicts **highest-sequence-wins** (`SkipList::try_insert_with_seq` / `insert_tombstone_with_seq`, plain `u64` comparison): a lower-sequence write applied later is dropped. Deletes go through `insert_tombstone_with_seq`, which creates the node *directly as a tombstone* when the key is absent from the memtable (so it still shadows lower layers) — there is no transient live placeholder. This makes the live winner for racing same-key writes identical to recovery's winner (recovery replays in sequence order), so a value observed live survives a crash. Non-WAL writes (TTL expiry, bulk, tests) allocate from the same counter (`KVStore::alloc_seq`) so there is one consistent sequence space.
- **At open the sequence counter starts above every STORED sequence, not just the WAL's.** The WAL's open-time scan (`Wal::open`'s highest sequence at or above the cut) sees only WAL entries, but a no-WAL write (`put_no_wal` / `delete_no_wal`) draws a sequence the WAL never records. After a crash the counter could restart below a no-WAL value already flushed to an SSTable, and every later write to that key — WAL-backed or not — lost to the stale value under highest-sequence-wins: an acknowledged put silently reverted, a delete silently undone, permanently once compaction baked it into L1. `KVStore::set_seq_counter` (called for every store at open and at namespace creation) raises the shared counter with `fetch_max(lsm.max_stored_seq() + 1)`; `max_stored_seq` is `max_lower_seq`, folded from every L0 and L1 file at open, and the memtable is empty then, so it bounds everything stored. Found 2026-10-10 by the M3a split crash audit while trying no-WAL meta writes in the split (a meta rewritten after a restart never became visible); every no-WAL user — vector payloads, the query-embedding cache — was exposed. Regression test: `a_write_after_a_crash_beats_a_flushed_no_wal_value` (`db/facade_tests.rs`), which fails without the raise.
- **The value log is SEGMENTED and segment ids are NEVER REUSED.** Each bucket is a series of immutable sealed segment files plus one active tail. A pointer is `bucket(32) | segment_id(32) | rec_offset(32) | value_len(32)`, so an address means one record *forever*: a superseded pointer still reads that key's own bytes, and a pointer into a reclaimed segment fails loudly (`ValueLogError::SegmentMissing`) instead of landing on another key's record. **This is the property the whole design rests on** — it is why there is no seqlock, no read-time seq check, no GC journal, no commit marker and no `.new`/`.old` recovery. `next_segment_id` is an in-memory `AtomicU64` seeded at open from `max(persisted high-water mark, highest existing id + 1)`; **never** derive an id from `max(files)+1` at runtime, or unlinking the newest segment hands its id out again and resurrects the recycled-slot bug.
- **Records store their KEY** (`[header 36B][value][key]`), which is what lets GC decide liveness per segment (one batched LSM lookup over the segment's distinct keys, `get_multiple`) instead of inverting the whole LSM. The value precedes the key so a read is **one pread of `36 + value_len`** — the pointer carries `value_len`.
- **Liveness lives in the LSM, not in the record.** There are no tombstone/updated flags. A write or delete that displaces a record just adds its size to that segment's garbage counter (`note_displaced`) — **zero I/O**, since the pointer carries `value_len`. Counters are a *hint* for GC selection; the exact live set always comes from the LSM (`rebuild_stats` recomputes them exactly when metadata is lost).
- **GC vs. writes/deletes.** `put_to_storage`/`delete_from_storage` hold the value-log **bucket write lock** across both the value-log append and the LSM insert/delete. GC holds the same lock across its CAS re-point (phase 2) — but NOT across its scan (phase 1), because the segment it is reading is sealed and immutable.
- **The L1 publish is ONE atomic rename — never move the live file aside first.** `merge_level0_to_level1` writes `level1_{b}.dat.tmp`, fsyncs it, then does a single `rename(tmp → level1_{b}.dat)` (`rename(2)` replaces the destination atomically) and fsyncs the L1 **directory** so the swap itself is durable. The bucket's L1 path therefore always names a complete SSTable — the old one before the call, the new one after, never nothing. The previous two-step publish (`rename(level1 → .old)` then `rename(tmp → level1)`) opened a crash window in which the L1 path did not exist: `LSMTree::open` would `create(true)` a 0-byte file, `file_len == 0` short-circuited the metadata load into "empty bucket", and `cleanup_old_files_on_startup` then **deleted the `.old` holding the only surviving copy** — silently losing every key that lived only in L1 (L0 survives; its `mark_obsolete()` comes after the renames, and the memtable replays from the WAL). Both a complete `.old` and a complete `.tmp` sat on disk unread. Regression test: `test_crash_between_l1_publish_steps_keeps_l1` — it watches the L1 path from a second thread during 200 compactions, because a *completed* merge removes its `.old` and so the final state proves nothing. `cleanup_old_files_on_startup` is now only a sweeper for `.old` files left by older databases.
- **Frame lengths are bounded before they are allocated from.** A frame is `[len u32][crc32 u32][body]`, and the CRC covers **only the body** — the length prefix is protected by nothing, so a flipped bit there is undetectable until after the payload has been read. Every reader therefore calls `check_frame_len(size, file_len)` before allocating: a frame can never be longer than its file. Without it a corrupt length requested up to 4 GiB from a file of a few dozen bytes (`valid_scan_start` already had a stricter inline form of the same check). Regression test: `test_corrupt_frame_length_is_rejected_before_allocating`, which asserts the guard's own error rather than the `Io(UnexpectedEof)` an unguarded reader surfaces *after* committing the allocation.
- **GC ordering is the crash-safety story (load-bearing).** `compact_bucket` → CAS re-point → `lsm.flush_memtable_to_level0()` → **only then** `unlink_segment`. At every crash point the durable LSM points at a segment that still exists, so there is nothing to roll forward or back. **Unlinking before the flush is data loss** (the durable LSM would point into a deleted file, and the WAL entries are long gone). Guard this with a test if you touch it.
- **L0 file stamps never go backwards.** Seq decides every conflict, but L0 file order (`created_at_ms`, which is also the file name) still breaks *exact seq ties* — and GC's relocation creates them, re-inserting a key at its existing seq with a new pointer. Raw wall time let a clock step backwards (NTP, a VM or WSL resume) between the original's and the relocation's flushes put the relocation first: every read returned the pre-relocation pointer, the L0→L1 merge baked it into L1, and after GC unlinked its segment the key read `SegmentMissing` for good. `LSMTree::next_l0_stamp` now clamps each stamp above the last one issued, seeded at open from the newest L0 file on disk; stamps are taken after the per-memtable flush lock and memtables flush in version order, so a later flush always sorts later. Do not reintroduce a raw `SystemTime` stamp. Regression test: `test_l0_order_survives_the_wall_clock_stepping_back`.
- **A read-only memtable is flushed to L0 once, and a second flusher WAITS for it.** The compaction worker, a GC pass and the no-WAL unpin all reach `flush_ro_memtable_to_level0`, and nothing else serialises them; its "already flushed?" check used to be unlocked, so two could write the same memtable (duplicate L0 files; in the same millisecond, one file name with the second `File::create` truncating the first mid-write). Each `ReadOnlyMemTable` now carries a `flush_lock` held across check + flush. It must stay a lock, not a "someone else is on it" skip flag: GC calls `flush_memtable_to_level0` and then unlinks segments, relying on the flush being durable on return — a caller that skipped would return before the other thread's fsync (the unlink-before-flush data loss above). Regression test: `test_concurrent_flushes_of_one_memtable_write_it_once`.
- **GC reinsert is compare-and-set and sequence-preserving.** GC re-points a key only if it *still* maps to the exact pointer it copied (`lsm.get_multiple`, batched, seq-resolved exactly like `get_with_seq`), and re-inserts under the key's **existing** sequence — so a relocation neither resurrects a deletion (key now absent → skip) nor reverts a newer write (pointer changed → skip) nor changes a key's version. The CAS runs under the bucket write lock, so it is atomic w.r.t. concurrent writers.
- **Cross-layer reads resolve by highest sequence, not layer order.** `get` / `get_with_seq` (`lsm_tree.rs`) gather the newest-`seq` entry across the active memtable, every read-only memtable, all L0 files, and L1, tombstone⇒`None` — they do **not** early-return at the first layer holding the key, because a GC re-point could (in principle) leave a low-seq value in a newer layer above a higher-seq tombstone. **Fast path:** an active-memtable hit whose `seq` is `>=` the per-tree `max_lower_seq` is authoritative and returns immediately — so normal writes (always newest seq) keep the early-return; only a GC re-point's low seq falls through to the full scan. `max_lower_seq` is the max seq of everything below the active memtable; its contract is **bound ≥ max seq of every lower layer**, so it is folded at flush (records leaving the active memtable) **and from every L0 *and* L1 file at open** — folding only L1 at open left it too low after a restart and let a low-seq active entry wrongly short-circuit above a higher-seq L0 tombstone (resurrection). Measured cost vs. layer-order resolution: ~5–10% on reads.
- **The slow path skips layers that cannot win — by bound, never by recency.** Past the fast path, `get_with_seq` / `get_multiple` still resolve by highest seq, but skip a layer they can prove irrelevant: RO memtables are binary-searched (`ReadOnlyMemTable::find`; the skip list dumps in `[u8]` order — `new` debug-asserts it); each L0 file carries an immutable `L0Summary` (min/max key, bloom, `max_seq`, sparse index) built when it enters the registry (`create_level0_file_for_records`, or `level0_file_summary` at open) and is skipped unread when the key is out of range / bloom-negative, or when a candidate already in hand has `seq >= max_seq` (`L0FileEntry::may_contain` / `cannot_beat`); L1 is skipped by the same `max_seq` test via `SStableMetadata::max_seq`. A file that *is* read starts from its sparse-index hint (`L0FileEntry::scan_start`), so a hit scans ~`SAMPLE_INTERVAL` entries rather than half the file — measured 16 L0 files × 2k keys: one L0 hit ~390 µs → ~6–10 µs. Each bound's contract is the `max_lower_seq` one — **too high is safe, too low resurrects**. The L0 summary cannot go stale because L0 files are write-once. L1's `max_seq` lives *inside* `SStableMetadata` on purpose: it is then published under the same lock as min/max, after the file swap and before the merged L0 files are marked obsolete, so a reader that sees stale metadata still sees those L0 files and has already folded their seqs in. Do **not** move it beside the file or publish it after `mark_obsolete`. Missing metadata or summary ⇒ no skipping. Do not cache an open fd per L0 file to save the `open` — a persistent fd per L0 file × bucket × namespace is exactly the EMFILE shape this repo has hit before, and the summaries already avoid most opens. Guards: `test_read_shortcuts_agree_with_brute_force_resolution` (random out-of-order seqs + re-points + flush/compact/reopen vs. a reference that reads every layer in full; it asserts each shortcut fired, and it catches a `max_seq` bound that is too low by one write) and `test_get_multiple_resolves_by_seq_not_layer_order`. Counters: `l0_bloom_rejects`, `seq_prunes` in `/admin/storage/ops-metrics`.
- **All same-key conflict resolution is by highest `seq`, never by layer/file recency.** Point reads (`get`/`get_with_seq`), batch reads (`get_multiple`), the GC liveness scan (`key_pointer_pairs`), and the L0→L1 merge (`merge_level0_to_level1` — both its cross-L0-file `by_key` collapse *and* `two_way_merge` with L1) all resolve a key's winner by the **highest global write `seq`** (`seq_newer`/`seq_newer_or_eq`; exact ties prefer the newer layer). This is sound because every write — WAL-backed and non-WAL (TTL/bulk/test) alike — draws from one global counter (`Database::next_seq` / `KVStore::alloc_seq`), so seqs are globally comparable.
  **`get_multiple` is on the GC data path — keep it seq-resolved.** Value-log GC decides segment liveness with it (`KVStore` compaction phase 1, and the phase-2 CAS under the bucket lock), since `0c5ebb8` batched those lookups for speed. It used to be *first hit by layer* (active memtable with no `max_lower_seq` check, RO memtables, L0 newest-by-`created_at_ms`, `lookup.remove` on the first hit), so a lower-seq tombstone in a newer layer answered "deleted" for a live key: GC then dropped the key's only record and unlinked its segment — **permanent loss**, the key reading `SegmentMissing` forever. The inversion is reachable: `delete_from_storage` allocates its seq *before* taking the bucket lock and TTL expiry sits outside the key stripe, so a TTL delete can apply after a higher-seq put was sealed below it (and L0 flush order is not seq order either). It also silently collapsed duplicate input keys to one position. Regression test: `test_get_multiple_resolves_by_seq_not_layer_order` (every layer boundary, plus a duplicated key).
  **L1 drops tombstones, so every writer must apply a key's writes in seq order (key stripe) or by compare-and-set (GC re-point).** Compaction into L1 discards tombstones because L1 is the bottom level, which is only safe while nothing can apply a *lower*-seq write to a key after its delete has reached L1: that write would then win and the deleted key would reappear. Today every writer satisfies this. WAL-backed and no-WAL writes hold the stripe from seq allocation through the memtable apply. GC re-points only a key whose current winner is the exact pointer it copied, under the bucket lock. WAL replay only covers a namespace's entries from its saved safe offset on, and WAL offset order is seq order, so a retired delete implies every earlier entry of that namespace is retired too; the per-namespace offsets (not just the global cut) are what keep a main-WAL put from replaying after a vector-index-WAL delete of the key reached L1 (`main_wal_replay_does_not_bring_back_a_key_whose_logged_delete_reached_l1`). TTL expiry takes the stripe and allocates its seq after a compare-and-set, so it satisfies this too. **A new writer that re-applies an old seq outside both the stripe and a CAS (a repair or import path, say) breaks this and silently resurrects deleted keys.** Do not "fix" it by keeping tombstones in L1; they would stay there permanently. The behaviour is pinned by the `Level1` cases of `test_get_multiple_resolves_by_seq_not_layer_order`.

- **`get_multiple` reads near its keys, never whole SSTables.** `resolve_bucket_batch` sorts each file's candidate keys and walks the file with one forward `FrameReader` cursor (`scan_sorted_candidates`), jumping to each candidate's sparse-index block (L1: `sstable_indexes`, computed under the read lock before any I/O; L0: `L0FileEntry::scan_start`) when that lies past the cursor. A hint is used only after `valid_scan_start` accepts it; a rejected one (an L1 file swapped by compaction) keeps scanning from the cursor, which is always below the current candidate, and bumps `sparse_hint_rejects`. It used to read the **entire** L1 file into a `Vec` per bucket for any batch — every doc-store query page (1–20 keys) paid several MB of reads: 1–14 ms per query on a 1M-document store, while the index evaluation took 0.3–3 µs; now 0.3–1 ms. Large batches (GC, vector candidates) degrade gracefully to one sequential read with 8–256 KiB refills, never a whole-file allocation. Guards: `test_get_multiple_reads_near_its_keys_and_agrees_with_get` (byte count for a one-key batch; batch sizes 1…all vs `get_with_seq`), `test_batch_scan_survives_bogus_hints`.
- **A write that loses its seq race must not touch the field index or the garbage counters.** The LSM drops a write older than the key's current copy, so reads keep showing the winner; the index must too. `put_to_storage_inner` and the delete body (`delete_with_bucket_locked`) both ask `LSMTree::current_pointer_and_wins` first and skip the index update and `note_displaced` when they lose. A winning **tombstone** counts as a winner there (`newest_copy` reports its seq): reading it as "absent, so any write wins" made a lost put index a key that reads as deleted, and a delete with no wins check stripped a live document from every query on the field — silent, and not healed by gap detection. Only TTL produced out-of-order seqs, and it no longer does, so this is defence in depth. Regression test: `test_a_write_that_loses_its_seq_race_leaves_the_index_alone` (`db/query.rs`).
- **The write sequence is `u64` end-to-end and must NOT be narrowed.** It is carried at full width through the memtable (`Node.sequence`, `KeyValueRecord.seq`), the SSTables (`SStableEntry.seq`), the value-log record header, and the WAL — so `seq_newer`/`seq_newer_or_eq` are plain comparisons. The LSM used to truncate to `u32` and compare with wrapping serial-number ("RFC 1982") arithmetic, valid only within 2^31. That reasoning holds for the memtable (it flushes long before 2 billion writes accumulate) but **not** for the SSTable levels: an L1 entry keeps its original seq for the lifetime of the database, so the gap to a later write of the same key is unbounded. Past ~2.1B lifetime writes (~2.5 days at 10k writes/s) updating a cold key made the *newer* write compare as older — `get` returned the stale L1 value and `merge_level0_to_level1` then baked it into L1 permanently, silently. Regression test: `test_write_after_huge_seq_gap_beats_cold_l1_entry` (`lsm_tree.rs`), plus `seq_comparison_spans_the_whole_sequence_space` / `insert_tombstone_seq_comparison_spans_the_whole_sequence_space` (`skip_list.rs`). Widening is free in memory — `u128` alignment already padded both structs (`Node` 48B, `SStableEntry` 64B, unchanged) — but it **did change the on-disk SSTable layout**; see *SSTable file format* below. **Recency is NOT a safe proxy for seq.** File `created_at_ms` is stamped at ro→L0 *flush* time, which can run out of seal/seq order (a higher-version memtable can flush to L0 before a lower one), and a GC re-point preserves a low seq into a newer layer — either leaves a lower-seq value in a "newer" file above a higher-seq tombstone. When the merge resolved by recency it baked the wrong winner into L1: it dropped the higher-seq tombstone and kept the lower-seq value → **resurrection of deleted keys** (the symmetric inversion made `key_pointer_pairs` treat a live value as dead → value-log GC drop = data loss). Confirmed by repro: a value's L0 file had a *larger* `created_at_ms` than the higher-seq tombstone's file. So keep these paths seq-resolved; do not reintroduce last-write-wins-by-file-order. **Scans too.** `scan_prefix`, `scan_prefixes`, `range_keys_bounded`, `range_pointers_bounded` and `key_pointer_pairs` all fold their layers through one helper, `fold_newest` (highest seq wins; layers are folded oldest→newest only so an exact tie goes to the newer layer), and `merge_scan_layers` applies the same rule to its bulk L1 merge. They used to overwrite by layer and relied on a per-record seq check on the value read that no longer exists, so a lower-seq copy in a newer layer (a TTL delete that lost its race, or L0 files ordered by a wall clock that stepped backwards — `created_at_ms` is `SystemTime`) hid live keys and surfaced deleted ones until the next merge. Guard: `test_scans_agree_with_brute_force_resolution`, which fails if `fold_newest` is made to overwrite.
- **SSTable lookups are tri-state** (`SsLookup::Found(ptr, seq)/Deleted(seq)/Missing`): both `Found` and `Deleted` carry the entry's seq so cross-layer resolution can compare them; an L0 tombstone must shadow a live L1 entry, so "deleted" and "absent" must stay distinct. The active memtable is checked via `SkipList::entry` (not `get_value`) for the same reason — a memtable tombstone must shadow lower layers.
- **Reads need no generation and no seq check.** `KVStore::get` resolves the pointer, reads it, and is done. A pointer whose segment GC reclaimed returns `SegmentMissing` → re-resolve through the LSM (which now holds the new pointer) and retry, bounded by `MAX_READ_ATTEMPTS`, then a lock-held read that excludes GC. Batch paths (`get_multiple`, scans) group by bucket, read in parallel, and re-resolve any key whose segment vanished mid-batch via single-key `get`. **A hard error in a batch (corruption, an IO fault, an LSM read failure) fails the whole call** — `KVStore::get_multiple`, both `Namespace::get_multiple`s, `AsyncNamespace::scan_prefixes_batch` and every `VectorKvStore` method return `Result`, and `semantic_search::service::search` propagates it. They used to map such errors to `None` or an empty map, so a corrupt key read as missing and a failed cluster scan read as "no matches" (`get_and_get_multiple_surface_corruption_instead_of_hiding_it_as_a_miss`). Keep "absent" and "failed" distinct. **Do not reintroduce a seqlock or a read-time record-seq comparison** — they were only needed because page offsets and slot ids used to be recycled.
- **The value log is fsynced before any WAL entry covering it is retired.** Writes fsync only the WAL; the value log follows `records_per_sync`, which is safe only while the WAL still holds the value. Recovery skips retired entries and WAL GC deletes them, so the value-log records an L0 flush points at must be on stable storage first. Four places guarantee it, all load-bearing for **power loss** (a process kill leaves the page cache intact, so the SIGKILL crash tests cannot see this): (1) `KVStore::set_flush_observer` wraps the observer in `SyncValueLogBeforePersist`, which fsyncs every bucket before passing on `on_ro_memtable_written` (where both WALs save their progress) — and vetoes the flush if the fsync fails, so the entries stay replayable; (2) `ValueLog::roll_active_segment` fsyncs the tail it seals, because `sync` only ever touches the *active* file; (3) GC fsyncs its relocated copies before flushing and unlinking (it appends them unsynced, and the unlink is made durable by a directory fsync — without this a power loss lost both copies); (4) `shutdown`/`Drop` fsync the value log before flushing the LSM. Before these, a power loss right after a flush could lose up to `records_per_sync` acknowledged values plus any segment sealed since its last fsync. Regression tests: `test_a_flush_to_l0_leaves_no_unsynced_values_behind`, `test_gc_makes_its_relocated_copies_durable`, `unsynced_bytes_track_what_a_power_loss_could_take`. **A new file's name needs a directory fsync too** — `sync_all` on a file makes its contents durable, not its directory entry. New WAL segments (`Wal::open_segment_file`, and the base file in `open_with_options_and_segment_size`) and new L0 files (`write_level0_file_for_records`, after the rename, plus parent directories it just created) now fsync their directory before anything that depends on them is acknowledged or retired; value-log segments and the L1 publish already did. Without it a power loss could drop a whole WAL segment of acknowledged writes, or an L0 file whose WAL entries were already retired. Not observable from a test; keep the fsyncs when touching these paths.
- **Group commit, never asynchronous commit.** Every `put`/`delete`/`merge` returns only once an fsync that *began after its entry was written* has finished; concurrent writers share that fsync. Path: append under the WAL lock (seq, frame, `begin_write`), release it, `note_write`, then `Database::commit_wal` → `Wal::commit` → `SegmentedLog::commit` (a commit round: snapshot the active file and tail under the log's append lock, fsync outside every lock, publish the durable position). `sync.commit_delay_us` (default 0) makes a leader wait only when others are waiting; `records_per_sync` tunes only the value-log fsync cadence. Load-bearing:
  1. **Apply to the memtable only after the commit returns** — a reader must never see a write a crash could undo (`an_acknowledged_write_survives_a_power_loss_and_an_unacknowledged_one_does_not`).
  2. **Leaving a segment fsyncs it** (`SegmentedLog::rotate`: end marker, fsync, then the next segment); a failed rotation poisons the log (`a_segment_filled_to_its_last_byte_is_durable_when_left`, `a_failed_rotation_poisons_the_log`).
  3. **A failed fsync poisons the log** (`KVError::WalPoisoned`): every writer in the round and every later one fails until reopen, and none is applied. `CommitRounds::commit` records the poison **before** it wakes the waiters, and re-checks it after a successful round (a waiter woken first would lead a round whose fsync succeeds over dropped pages). Guards: `a_caller_waiting_on_a_failed_round_never_leads_another` (deterministic: the `after_failed_round` test hook holds the leader until the waiter is done), `a_round_that_finishes_after_the_log_is_poisoned_fails`.
  4. **Saved progress can pass the durable tail after a failed fsync** — the failed writer releases its in-flight registration while its frame stays in the live tail, so a later flush saves a cut past what is on disk. `SegmentedLog::open` starts a new segment when `OpenFrom::furthest` is past the recovered tail (`progress_saved_past_a_failed_fsync_does_not_hide_later_writes`).
  5. **Coverage is checked in every test:** `SegmentedLog::commit` asserts the fsyncs actually issued covered every acknowledged byte (`covered`), and the power-loss model (`Database::power_loss_image`) cuts each log back to them. Fsync sharing is tested with a simulated fsync cost (`Wal::set_fsync_delay`), not the machine's disk.

## SSTable file format

```text
[header 16B: magic "MSST"(4) | format_version u32(4) | reserved(8)] [frame] [frame] ...
frame: [u32 payload_len][u32 crc32(body)][body = rkyv SStableEntry]
```

Every **non-empty** SSTable (L0 and L1 alike) starts with the header; entry frames begin at `SSTABLE_DATA_START` (16). A freshly created, never-written L1 file is 0 bytes and carries no header — `file_len == 0` means "no entries" and stays valid. `SStableMetadata` is in-memory only, rebuilt by scanning the file at open.

**Why the header exists.** The entry CRC covers only the body, so it cannot detect a *layout* change: the bytes are identical and only their interpretation differs. Before headers existed, widening `SStableEntry.seq` from `u32` to `u64` meant an old file still passed CRC and was then handed to `rkyv::access_unchecked` under the new layout — garbage fields, no error. `validate_sstable_header` now rejects a bad magic (what a pre-header file looks like) or an unknown version with `LSMError::Corruption`. **A database written before the header existed cannot be read; recreate it** — the greenfield policy (no migration tooling) permits that, and it now fails loudly instead of silently.

**Bump `SSTABLE_FORMAT_VERSION` whenever `SStableEntry`'s layout changes.** Nothing else detects it.

**Headers are validated once per file, not once per read.** A file's format version is fixed when it is written and cannot change afterwards (L0 files are write-once and are unlinked only once `readers() == 0`), so the header is checked when a file *enters* the Level-0 registry, never again. Two openers encode this:

| Opener | Validates | Cursor | Use for |
|---|:---:|---|---|
| `open_sstable_for_scan` | ✅ | `SSTABLE_DATA_START` | first touch — L1 files, and on-disk L0 files scanned during `LSMTree::open` |
| `open_registered_l0` / `open_registered_l0_for_scan` | ❌ | 0 / `SSTABLE_DATA_START` | any path holding an `L0FileEntry` (all read/merge paths) |

The two registry entry points are what establish the invariant: `load_existing_level0_files` validates every on-disk L0 file at open, and `register_level0_file` only ever receives a file this process just wrote with a header. **Do not register an L0 file from anywhere else without validating first**, and do not point the registered-file openers at an unvetted path — a foreign layout would be parsed as entries with nothing downstream to catch it. Measured: re-validating on every read cost **+147 ns per L0 file access (+28%)**, paid on every point get reaching L0 for each L0 file its summary cannot rule out; validating once is back to baseline (+0.2%). L1 never paid it — its handle is cached as an `Arc<File>` in `sstable_files[bucket]` and validated once at open.

Because reads no longer re-check, `LSMTree::open` is the **sole** guard against a pre-header database; `test_open_rejects_l0_file_written_in_an_older_format` pins it. Note this also means a test that wants a *registered* L0 file to fail a read must corrupt it while keeping a valid header — a headerless body just reads as EOF past `SSTABLE_DATA_START` (see `test_compact_bucket_resets_flag_on_merge_error`).

Two more invariants to preserve when touching SSTable I/O:
- **Scans that start at the head of a file must begin at `SSTABLE_DATA_START`, not 0.** Starting at 0 reads the magic as a frame length (~1.4 GB) and hangs on the allocation. Both `*_for_scan` openers position the read cursor for sequential readers; positional readers (`read_exact_at` with their own offset) skip the seek and must start their offset there themselves.
- **Sparse-index offsets are absolute file positions** (seeded with `SSTABLE_DATA_START` at write time in `write_merged_sstable` for L1 and `create_level0_file_for_records` for L0, and rebuilt the same way in `load_metadata_from_file`), so seek-based readers need no adjustment. Keep all three in agreement, or every sparse hint lands off target. **A wrong offset never gives a wrong answer** — `valid_scan_start` rejects the hint and the lookup falls back to a full scan — so on its own it would show up only as lost speed. Three things keep it visible. (1) An L0 file is never rewritten, so its hint has no legitimate way to fail: `lookup_in_sstable_file_path` `debug_assert!`s that it did not, which turns every debug test reaching an L0 lookup into a guard (with offsets planted 4 bytes off, 19 lib tests fail; before the assert only the dedicated test did). Do not put that assert on the L1 path — an L1 hint legitimately goes stale while a compaction swaps the file, and `test_sparse_index_stale_hint_falls_back_correctly` feeds bogus hints on purpose. (2) Every rejection, L0 or L1, bumps `sparse_hint_rejects` in `/admin/storage/ops-metrics`: expected only briefly for L1 during a compaction, so a steady rate in production means the offsets are wrong. (3) `test_l0_sparse_index_hints_are_valid_and_survive_reopen` pins the L0 pair directly (flush-time and open-time indexes must agree, every hint must be a valid scan start).

`LSMTree::open` validates the header explicitly for each non-empty L1 file and propagates the failure. The metadata load right after it is deliberately lenient (`if let Ok(..)`) so a partially-written tail leaves the bucket without a sparse index rather than failing open — that leniency must **not** be extended to cover header validation, or an unreadable file silently becomes an empty bucket. Regression tests: `test_pre_header_sstable_is_rejected_not_misread`, `test_sstable_with_unknown_format_version_is_rejected`, `test_open_rejects_l1_file_written_in_an_older_format`.

**Both levels publish a file by rename, so a `.dat` at its final path is always whole.** L1 is written to `level1_{bucket}.dat.tmp` and renamed. L0 is written to `{stamp}.dat.tmp`, fsynced, renamed to `{stamp}.dat`, then its directory fsynced (`write_level0_file_for_records`), and `load_existing_level0_files` deletes leftover `.dat.tmp` files at open. L0 used to be written **in place**, and a process killed mid-flush left a `.dat` cut anywhere — inside a frame body too, since a kill can land mid-`write`. Every reader treats EOF inside a frame as an error (only a clean EOF at a frame boundary ends a walk), so the next open failed and kept failing until the file was removed by hand: `Corruption("frame declares a N-byte payload in a M-byte file")` when the cut frame was longer than the file, otherwise `level0_file_summary` mapped the `UnexpectedEof` to "no summary", registered the file anyway, and recovery's merge hit `LsmError(Io(UnexpectedEof))`. Found 2026-10-26 by `acknowledged_writes_survive_repeated_kills` (1 run in 200, ~1 kill in 800; 0 in 800 runs after the fix). Deleting a `.dat.tmp` is safe because the flush retires its WAL entries only *after* every bucket file is renamed and fsynced (`flush_ro_memtable_to_level0` → `notify_ro_memtable_written` → `WalPersistObserver::prepare_written`), so its records are still in the WAL and replay restores them. **Don't make open tolerate a torn `.dat` instead**: a damaged length prefix in a complete, retired file looks the same as a torn tail, and setting that aside would lose data silently; with the rename a torn `.dat` can only be damage, which must fail the open. The short-header skip (a `.dat` shorter than `SSTABLE_DATA_START`, `warn!` and not registered) stays for files a build that wrote L0 in place left behind; it must **not** be widened into tolerating a bad magic at full length, or a pre-header database would quietly come up with empty L0 buckets instead of being rejected. Regression tests: `test_open_removes_a_level0_file_a_kill_left_unfinished`, `test_open_skips_a_crash_truncated_level0_file`.

- **The worker merges a bucket's L0 into L1 only when it is due — never on every seal.** `merge_level0_to_level1` rewrites the bucket's *whole* L1 file, so its cost is the size of L1, not of what was flushed. The worker used to merge every bucket holding any L0 file on every tick, and every memtable seal triggers a tick; the vector worker's durability barrier (`make_vector_writes_durable`, one flush of three namespaces per batch, and a batch is one document at low load) then flushed ~13-entry memtables several times a second. M5 measured, at 50 requests/s, 10 flushes and 16 merges a second, ~2 MB rewritten per document written, **93% of all disk writes** (2026-10-15). Now the worker calls `compact_due` (`LsmCompactionTarget::compact_due` → `Database::compact_lsm_due` → `KVStore::compact_lsm_due` → `LSMTree::compact_due`): it still flushes every read-only memtable (they pin the WAL) and releases flushed ones, but merges only buckets where `compaction_due` holds — live L0 entries ≥ `L0_COMPACTION_RATIO_PERCENT` (10) % of L1's entries, which bounds the rewrite to ~10× what was flushed, **or** ≥ `L0_COMPACTION_MAX_FILES` (8) live L0 files, which bounds what a point read may open (an L0 file without a summary counts as due). An empty L1 takes any L0. `compact_all` (shutdown, `Db::compact_lsm`, tests) still merges everything. L0 entry counts come from `L0Summary::entries` (from the records at flush, `entry_count` at open). Consequence for readers of stats: L0 is normally non-empty now. Tests: `small_flushes_wait_until_level0_is_a_share_of_level1`, `many_tiny_flushes_are_merged_at_the_file_cap`, `compact_all_merges_what_compact_due_leaves`. The flush rate itself (fsyncs, small files) was the barrier's; the vector worker now makes its writes durable with one fsync of the vector index WAL instead (`db/vector_index_wal.rs`).

> **Test note:** `compact_all()` drains only *read-only* memtables and L0 — it does **not** seal the active memtable, and returns early when both are empty. A test that wants data in L1 must call `flush_memtable_to_level0()` first, then `compact_all()`, and should assert the L1 file is non-empty rather than assuming it. Skipping the flush silently exercises the skip list instead.

> **Test note:** `AsyncDb::crash()` must lose exactly what a process kill loses. Each `KVStore` flushes its memtable in `Drop`, so a crashed database marks its stores (`Database::mark_crashed` → `KVStore::mark_crashed`, test-only) and their `Drop` skips the flush. Until 2026-10-11 it did not, every unflushed no-WAL write survived a simulated crash, and no crash test could catch a missing barrier flush. Any new `Drop` that writes must honour the flag. Regression test: `a_simulated_crash_loses_unflushed_no_wal_writes`.

## Typed value API

`put_typed<T>` / `get_typed<T>` / `merge_typed<T>` use `rkyv` for zero-copy serialisation. Types must derive `rkyv::Archive + rkyv::Serialize + rkyv::Deserialize`. These are re-exported via `minnal_db::rkyv_derives` so downstream crates don't need a direct `rkyv` dependency.

## Scan / read API

Two families of multi-key reads, differing in **memory profile**:

- **Unbounded** — `scan_prefix_batch` / `scan_range_batch` (facade: `scan_prefix` / `range`) materialise the *entire* matching result set — keys **and all values** — in one `Vec`. Memory scales with total matches. Use only when the result is known-small or genuinely needs to be whole.
- **Bounded (cursor-paginated)** — `scan_page_batch(cursor, end, limit)` (facade: `Namespace::scan` / `AsyncNamespace::scan`) returns at most `limit` pairs plus a `next_cursor` (the raw key the next page starts at, or `None` at the end). **Each page resolves only its own values**, so peak memory is O(page), not O(total). Prefer this for anything user-facing or unbounded. `end` (exclusive) bounds the scan to `[cursor, end)`; a prefix scan passes the prefix's upper bound (`minnal_db::prefix_upper_bound`) as `end` so it stops at the prefix instead of walking the keyspace tail.

Semantics: cursor pagination is **read-committed across the walk**, not a point-in-time snapshot — a key deleted/overwritten between pages reflects the newer state (each page is its own generation-stable read + `refetch_dropped` fallback). Acceptable here because writes are single-op (no transactions).

POINTER-RESOLUTION INVARIANT (load-bearing): the LSM scan returns value-log *pointers* that are LSM-complete but **must be resolved inside the same `read_generation_stable` bracket** (or under the value-log bucket write lock). Resolving a pointer outside that bracket reopens the wrong-file window closed in `420ac8e`. The `end` bound added for pagination only filters keys in the LSM merge — it does **not** change this resolution rule.

Caveat (not yet fixed): `scan_page_batch` bounds the *value* memory per page, but the LSM merge still builds a keys+pointers map for everything `>= cursor` before `take(limit)` (no values — the small cost, shrinks as the cursor advances). Bounding that transient is the deferred "bounded k-way merge" follow-up; resolve every key with `fold_newest` (highest seq), never by layer order, and keep folding oldest→newest so an exact seq tie goes to the newer layer — see [`lsm_tree.rs`](src/store/lsm/lsm_tree.rs) `fold_newest`.

## Namespaces

Each `Db` has a default namespace plus any number of named namespaces. Each namespace has its own keyspace. Field indexes are registered per-namespace via `Db::register_field` / `Db::register_extractor`.

`remove_namespace` reclaims on-disk storage (the `ns_{name}` data dir + `index/{ns_id}` subtree). The step order is load-bearing for crash safety: **persist the registry deletion first**, then flush/drop the store, forget it in the WAL observer (`forget_namespace`, so it stops holding the cut), and only then delete files. Recovery skips WAL entries whose `namespace_id` is absent from the registry (`recover_from_wal`), so a crash mid-cleanup never resurrects the namespace. File deletion never touches the shared WAL — keep it that way.

A crash before `forget_namespace` leaves the dropped namespace's entries above the saved cut, which is **not a permanent WAL leak**: the next startup's recovery skips them (unknown namespace) and then retires the whole log (`retire_all`, cut = tail), so WAL GC reclaims those segments on its next cycle.

## Row IDs

By default, field-index row IDs are **dense, monotonic** integers (0, 1, 2, …) assigned per namespace by a `RowMap` sidecar (`index::RowMap`, on disk under `index/{ns}/rowmap/`). Dense IDs make the RoaringBitmaps pack into a few containers instead of scattering one-per-doc, which is the whole reason field-index bitmaps stay small. `resolve_row_id_alloc` (put/replay) allocates on first sighting; `resolve_row_id_get` (delete/query fallback) never allocates; `query_keys` resolves hits back to keys via `RowMap::key_for` (O(|hits|)).

The map is a **derived** structure with the same durability model as the field index: writes mutate mmap in memory, flushed at the index checkpoint, rebuilt by WAL replay on open. **Load-bearing ordering:** `run_index_checkpoint` flushes the row map (advancing its `rowmap.ckpt` marker) **before** any field index, so the map is always at least as durable as every persisted bitmap bit — otherwise a crash could leave a bit whose row ID can't be reproduced.

The `key → id` slot table is **file-backed (`rows.slots`) but never adopted from disk** — `open` recreates it with `.truncate(true)` and rebuilds from the durable id array, so it is never a persisted source of truth. The file backing is purely to keep ~34–69 bytes per distinct-key-ever-written out of *anonymous* memory (measured: 1M keys ⇒ 48 MiB slot file, **0 MiB anonymous RSS**; 10M ⇒ 384 MiB, rebuilt at open in ~1.3 s release/page-cache-warm). Anonymous pages can be swapped but never dropped; file-backed pages the kernel can evict and re-read. A slot is **24 packed bytes** — `id+1` (0 ⇒ empty, which is why a zeroed file is a valid empty table), `key_off`, `key_len`, and a 32-bit hash tag. Every field is read via `from_le_bytes` on a byte slice, so there is no alignment padding to add back; and the layout is free to change *because* the table is rebuilt at open, so nothing persisted depends on it.

**Do not "optimise" the rebuild away.** A `MAP_SHARED` mapping is written back by the kernel at will with no inter-page ordering, so after a crash the file can hold entries for uncommitted ids or a half-finished rehash — and unlike the append-only `keybytes`/`idarray`, scattered hash positions give no length-based cut that separates good entries from stale ones. Adopting one hands back an id the id array lacks: silent, permanent bitmap/key divergence that **WAL replay cannot heal, because replay adds entries and never removes them**. This is *not* solved by FR-001's WAL-retention guarantee — that fixes a missing tail; this is unproven content. Trusting the file needs a real commit protocol (in-file CLEAN/DIRTY header msynced before the first slot mutation, plus `header.next_id == marker.next_id`), deliberately not built because after a crash the table is DIRTY by construction and rebuilds anyway — it would only speed up a clean restart. Pinned by `open_rebuilds_the_slot_table_and_never_adopts_stale_entries`. See `index::RowMap` docs.

**IDs are freed only by a whole-map reset, with no field index in the namespace (FR-006).** `Database::reset_rowmap` refuses unless every registered field of the namespace is dropped and none is active (row IDs are referenced only by field bitmaps; gap records and build progress store keys; writers resolve an ID only while a field is active, under the `namespace_index` read lock), and holds `index_activate_lock` throughout. `RowMap::reset` removes `rowmap.ckpt` first and fsyncs the directory — the commit point, since a missing marker opens as a fresh map — then `create` truncates the files. The old `RowMap` is dropped before the truncation so no mapping outlives its file. Never free individual IDs: a bitmap can still hold a deleted key's ID (a delete not on disk at a crash, an unrepaired gap), and replay never clears bits, so a reused ID silently matches the old key's values. The doc store's `reindex_all_attribute_indices` (crash-safe via `index/{ns_id}/reindex_all.json`, finished by `resume_pending_builds`) and `drop_all_attribute_indices` call it.

**Escape hatch (unchanged):** register `RowIdFn` + `RowToKeyFn` together to bypass the row map and derive the ID directly from the key — O(|hits|) query resolution with zero map. Use it only for keys that are already dense or clustered (the doc store does so for `u64` keys only): random keys such as v4 UUIDs put every row in its own bitmap container, so every value's bitmap and its directory grow with the document count. `uuid`/`u128` doc stores used it until 2026-10-09 (`helpers.rs::activate_indices`); a 1M-doc load showed 33 MB for a two-value field at 250k docs. These are the only two row-ID sources (`resolve_row_id_alloc`/`resolve_row_id_get`): a `RowIdFn` if registered, otherwise the dense `RowMap`. The row map is always loaded before any field is activated (`ensure_rowmap` in `activate_field_index`), so an indexed namespace always has one or the other — resolution never falls through. (The old Murmur3 `key_to_row_id` fallback was removed once dense row IDs became the default.)

## Sharding

`num_buckets` (default 16) shards both the value log and LSM SSTables. Keys are hash-distributed. **Cannot change `num_buckets` on an existing database** — the value is locked at creation time.

**The bucket is chosen from the FIRST 8 BYTES of the key only.** `get_bucket_for_key` (`support/mod.rs`) hashes `key_prefix_of(key)`, which zero-pads or truncates to 8 bytes; the same 8-byte prefix is what `SStableEntry.key_prefix` carries for fast comparison, so this is a deliberate performance choice, not an oversight. The consequence is a **key-design rule that callers must be told about**: keys whose first 8 bytes are constant all land in the *same* bucket, however many buckets are configured — one hot LSM shard, one value log absorbing every write, and unbalanced compaction. Fixed-width integer and UUID keys spread well by construction. String keys (`KeyType::Str`, `KvKeyType::Str`) do not, if they are built the way people naturally build them:

| Key shape | Effect |
|---|---|
| `user:profile:a3f9…`, `job_content_…` | ✗ constant leading 8 bytes → one bucket |
| `a3f9-user-profile`, `2026-08-03-job` | ✓ varying leading bytes → spread |

Guidance: put the varying part of the key first, or keep any constant prefix under 8 bytes.

The value log's **segment size** (`DbConfig::segment_size_bytes`, default 256 MiB) is by contrast **not** locked at creation: it is not encoded in any pointer (only a segment id and a byte offset are), so existing segments keep the size they were written at and new ones use whatever is configured now. It bounds GC's unit of work and the file/fd count.

## Value-log GC thresholds (two knobs, not one)

`value_log_waste_threshold` (default 30%) is the **trigger** — whether a bucket is collected at all. `segment_gc_threshold` (default 10%, `ThresholdConfig::segment_gc_threshold`) is the **selection** rule — whether an individual sealed segment is rewritten. They are passed to different places: the trigger is compared against `get_waste_ratio()` in `Database::run_gc_if_needed`; the segment threshold is what `garbage_collect_with_threshold(s)` takes and `compact_bucket` compares each sealed segment against (via `ValueLog::gc_candidates`). (A third knob, `tail_gc_min_garbage_pct`, decides when the never-full active tail is sealed early so its garbage becomes collectable — resolved by `ThresholdConfig::effective_tail_gc_min_garbage_pct`.)

**Keep the segment threshold below the trigger.** A segment under it is "clean" and is left in place *with its garbage intact* (its live records keep their pointers). They used to be the same value, which made garbage just under the trigger permanently uncollectable — every pass skipped those segments, reported success, and left the bucket still over its trigger. Measured: 14.6× write amplification with 11.8 MiB stranded at a 30% segment threshold; 5.3× and 1.1 MiB at 10%. Regression test: `gc_reclaims_garbage_below_the_bucket_trigger` (`tests/gc_reclaim.rs`).

## Background workers

All background workers (`lsm_worker`, `gc_value_log_worker`, `wal_worker`, `ttl_worker`, `index_checkpoint_worker`) are spawned on `Db::open` and stopped on `Db::shutdown`. Always call `shutdown()` — dropping without it may lose buffered writes.

**A worker's pass runs through `support::run_blocking_pass`, never plainly in its task.** Passes are file I/O (fsyncs, flushes, merges, segment rewrites), and run on a runtime thread they held up every task queued on that thread. M5 traced every `get` over 15 ms (p99 4–10 ms against a 1.3 ms median, varying run to run) to the index checkpoint: ~55 ms of fsyncs every 1.75 s, and requests arriving during it finished only when it did (2026-10-17). The helper uses `block_in_place` on a multi-thread runtime (the thread's queued tasks move to another thread) and runs inline on a current-thread one. **Not `spawn_blocking`:** its closure holds the database alive past its last handle while a pass runs, so a store dropped without `shutdown` and reopened at once had the old instance's final flush and compaction running under the new one (two doc-store restart tests failed intermittently with `NotFound`). The TTL worker predates this and uses `spawn_blocking`. Guards: `a_checkpoint_does_not_block_the_runtime`, `a_compaction_pass_does_not_block_the_runtime`, `a_gc_pass_does_not_block_the_runtime`, `a_wal_gc_pass_does_not_block_the_runtime` (all four fail with a plain call). A pass still holds the `Db` while it runs, so the doc store's directory lock (`DirLock`) is held by the `Db` (`AsyncDb::hold_dir_lock`, a field declared after `inner`), not the `DocStore`: it is released only once the database has finished dropping, and a reopen meanwhile fails with `StoreLocked` instead of sharing the files. Guard: `the_lock_is_held_while_anything_still_holds_the_database`.

Each worker is a **single global task** that fans out over namespaces — there is no per-namespace worker. `ttl_worker` follows the same shape as `gc_value_log_worker`: one `TtlWorker` task (handle in `Database::ttl_worker`) driven by `TtlTarget::run_ttl_pass`, which iterates `NamespaceRegistry::ttl_configs` (`ns_id -> (Duration, max_deletes_per_run)`) and calls `KVStore::expire_records` for each TTL-enabled namespace.

**TTL config is persisted** in the namespace registry file (`RegistryData::ttl_configs`), not just held in memory — it survives restarts. The registry — not `store.ttl` — is the source of truth for what the worker processes: `namespace_with_ttl` calls `registry.set_ttl_config` (persists) and starts the worker on first use; `shutdown_ttl_worker(ns_id)` calls `remove_ttl_config` (persists, stops expiring that namespace without killing the task); `remove_namespace` drops the config as part of `registry.remove`. On open, each store is reopened with its persisted ttl (`open_with_ttl`) and `enable_all_workers` restarts the worker when any TTL config exists. **Do not clear `ttl_configs` on shutdown** — that would wipe the durable config. The worker only starts when at least one TTL namespace exists, so a database with none runs no TTL task. (Sync-mode `Db::namespace_with_ttl` has no `max_deletes` and no worker, so it sets `store.ttl` in memory only and is intentionally *not* persisted.)

## WAL ownership

**Both WALs are one log format: `db/segmented_log.rs` (`SegmentedLog`); the reader-facing design is `docs/WAL-Architecture.md`.** Everything about how bytes reach the disk and come back after a crash lives there once; each log adds only a `LogFormat` (name, magic, body version), a body encoding and its own retirement. A new log (another index, say) should be a `LogFormat` plus a body codec on top of it — do not copy segment, frame or open logic into a log module. Its load-bearing rules:
- **Positions are `(segment_id << 32) | byte`** (`position`, `split`, `segment_of`, `segment_start` = byte 16, past the header), so the segment size is not baked into positions and can change between opens (no creation-time marker; `test_wal_segment_size_can_change_between_opens`). Cuts compare as plain `u64`. Operators see `LogPosition {segment_id, byte}` in both logs' stats.
- **Every segment has a 16-byte header** (magic, version, id checked against the file name): a segment of another log or format version fails the open (`a_segment_from_another_log_fails_the_open`, `foreign_or_missing_segments_fail_the_open`). **Bump `LogFormat::version` whenever a body layout changes** — nothing else detects it.
- **Segments are preallocated, and the end marker is `len = u32::MAX` (`END_MARKER`), not 0** (design note §18). A segment is created at full size; past half of the active one, `SegmentPrep` zero-fills the next as `{id:010}.log.prep` with its header, and `rotate` installs it (the `.prep` name keeps a half-written file out of the log; open deletes leftovers). So `len == 0` means *unwritten space* (`WalkEnd::Unwritten`): in the last segment that is the tail, in an earlier one it is "not sealed" corruption. The marker's four bytes are reserved when deciding whether a record fits (`max_frame_len`), and **a sealed segment is fsynced before the next one is created**, so only the last segment can hold unsynced bytes: open calls a bad frame there a torn tail and a bad frame anywhere else corruption (`a_bad_frame_before_the_last_segment_fails_the_open`; the main WAL used to cut the log there and silently delete every later segment). A gap in the segment ids is corruption too (`a_missing_middle_wal_segment_fails_the_open`). A new segment's header and directory entry are fsynced before any record goes in, so a short, headerless or **all-zero-header** *last* segment holds nothing and is recreated. A segment's file length says nothing about how far it is written: use `segment_end` / `sealed_ends`, never `metadata().len()`.
- **`open` zeroes everything past the tail of the last segment** (`zero_past`: `set_len(tail)` then back to full size), torn or not. Ignoring it is not enough: a power loss can keep pages past a lost record, and same-size records later laid over the gap end exactly at an old record's start, which then replays (`records_past_a_lost_one_never_rejoin_the_log`, `open_truncates_a_torn_tail_so_stale_frames_cannot_replay`).
- **Open reads only from the cut** (`OpenFrom::cut`; the whole last segment, to find the tail): segments wholly below it are retired and not read, so damage there does not fail the open, and a log's highest seq covers unretired records only — retired ones are in SSTables, which raise the counter themselves, and the main WAL also saves its high-water mark (`WalMetadata::last_sequence`) on every metadata save (`a_write_after_a_reopen_beats_entries_below_the_cut`). **No saved progress (`cut: None`) with segments starting above 0 fails the open**: the cut is unknown, and replaying what is left could bring back retired entries (`lost_wal_metadata_after_gc_fails_the_open`). A cut below the oldest segment is corruption.
- **A cut past a sealed segment's end marker is legal** (open sealed the segment at the durable tail because saved progress named lost positions): a walk that finds unwritten space *exactly where it starts*, in a segment whose marker lies at or below that start (`sealed_at_or_below`), is fine, in both `open` and `for_each`. Guards: `progress_past_the_durable_tail_starts_a_new_segment` (reopens twice), `a_marker_past_the_durable_tail_starts_a_new_segment`.
- **Progress files are one format** (`ProgressFile`: magic, version, cut, sorted `(ns, safe)` list, extra bytes, CRC; `Progress::open_from` builds `OpenFrom`). Decode rejects a safe offset below the cut and unsorted namespaces (`a_progress_file_round_trips_and_rejects_damage`). The main WAL's `wal/metadata` (magic `WALM`) adds its GC counters and sequence high-water mark as extra bytes; the vector WAL's `retired_cut` (`MVIC`) adds none.
- **The main WAL saves neither head nor tail.** Open takes the tail from the log and the head from the oldest segment on disk (`Wal::head`; `the_head_is_the_oldest_segment_on_disk_after_a_reopen`). `WalMetadata.tail` is the in-memory mirror of the log's tail, kept under the WAL lock because the cut's readers (`wal_cut_ceiling`) need the tail and the in-flight set to agree.
- **Missing or unreadable main-WAL metadata with L1 data fails the open** (`open_main_wal`): the cut is unknown, and replaying the whole log could resurrect a key whose delete reached L1, where compaction dropped its tombstone. With no L1 data (a new database, a crash during its first flushes) the log is replayed whole, keeping the damaged file as `metadata.corrupt`. Guards: `unreadable_wal_metadata_with_l1_data_fails_the_open`, `unreadable_wal_metadata_without_l1_data_replays_the_log`, `lost_wal_metadata_after_gc_fails_the_open`. The configured segment size must lie in [64 KiB, 4 GiB] (`Wal::validate_segment_size`; tests use smaller ones through `Database::open_with_wal_segment_size`).
- **Errors:** `LogError` is the log-level error; each log wraps it in one variant (`WalError::Log`, `VectorIndexWalError::Log`) instead of mirroring its variants. A reader whose error does not convert from `LogError` passes a mapping to `for_each_with`; no wrapper types.
- **One frame walker** (`walk_segment`) serves `open` and `for_each`, and bounds every length by the bytes left before allocating. `for_each` skips segments below the oldest on disk (retired; a reader racing GC re-lists and skips the same way) and calls a missing segment above it corruption; `missing_segments` reports the holes for a caller that must know (field-index replay). Never re-implement the loop for a new scan.
- **The power-loss model records real fsync coverage** (test-only `written` / `synced` per segment, `first_open_segment`): `lose_unsynced` and `power_loss_extents` cut each segment to what an fsync covered, and `commit` asserts `covered(end)` — every earlier segment through its marker, `end`'s segment to `end`. A stress that snapshots "synced" records must take the list *at* the power loss: writers frozen inside a commit finish after the image.
- **`commit` / `sync` run as commit rounds** (`CommitRounds`, design note §16): the fsync runs outside the append lock, concurrent callers share one fsync, and a call returns early when nothing was appended since the last fsync. `append(body_parts, under_lock)` takes the body as slices (one copy into the frame) and runs `under_lock(start, end)` before publishing the tail, which is where a log registers a record as not yet applied.

All main-WAL logic (append, GC, recovery, sequence tracking) lives exclusively in `database.rs` (`Database`, the internal coordinator) on top of `Wal`. The one other log, the **vector index WAL** (the vector worker's no-WAL payloads, made durable by one fsync per batch instead of a memtable flush), lives in `db/vector_index_wal.rs`, and `database.rs` only calls it at open and from the GC tick (design: `src/semantic_search/report/Vector-Index-WAL-Design.md`). Do not add WAL code anywhere else.

**Vector index WAL specifics.** Segments `vector_index_wal/{id:010}.log` (magic `MVIW`), body `[ns_id|seq|key|value]` (a delete: `value_len = u32::MAX`, no value). `sync` makes every append that *returned before the call* durable (`syncs_waiting_together_share_one_fsync`). `unretired_bytes` counts record bytes from the retired cut (headers and end markers excluded). Its counters (`vector_wal_appends`, `_bytes_appended`, `_fsyncs`, `_gc_runs`, `_segments_deleted`, `_pin_flushes`, `_records_replayed`, `_records_skipped`) are bumped only on the database's global `Metrics`. Guard for reading from the cut: `open_does_not_read_segments_below_the_cut`.

**A failed fsync poisons the log** (`VectorIndexWalError::Poisoned`): appends and syncs fail until the database is reopened; stats report `stopped`. After a failed `fsync` the kernel may have dropped the dirty pages, and a later successful `fsync` says nothing about them — advancing `durable_tail` past them let later batches complete over a hole that `open` reads as a torn tail (dropping those batches' records). PostgreSQL's reasoning. Guard: `a_failed_fsync_stops_the_log_until_it_is_reopened`.

**Vector index WAL retirement rules (step 2).** Every database opens the log (`Database::open_vector_index_wal`, both constructors) and every namespace's `LsmFlushObserverHub` reports seals and flushes to it; the log tracks a namespace from its first append and ignores the rest. Load-bearing:
- **The seal records a *per-namespace* ceiling** (tail lowered to that namespace's oldest append not yet applied), not the main WAL's global one. With a global ceiling, a namespace sealed while another namespace's write was in flight kept `safe_offset < last_write` after flushing *everything* it wrote; its memtable was then empty, so no later flush could seal it again, and an idle namespace held the cut — and every later segment — for good. Sound because the seal callback runs under the memtable's write lock (`flush_memtable`), so no record can be applied into the next memtable meanwhile. `LoggedWrite` (returned by `append`, registered under the append lock, cleared on drop) is what makes "not yet applied" visible. Guard: `another_namespaces_record_in_flight_does_not_hold_a_flushed_namespace` (fails with the global ceiling).
- **A flush with no seal record retires nothing** (it only lets later versions fold past it). Recording the current ceiling there, as the main observer does, would claim records applied into the *next* memtable — reachable when the namespace's first append lands between a seal and its flush. Guard: `a_flush_without_a_seal_record_retires_nothing`.
- **The cut is written to `retired_cut` before it is published**, and GC reads only the published cut, so a segment is never deleted past a durable cut. At open, a cut past the tail, below the oldest segment, or a missing marker with segments starting above 0 is corruption.
- **`open` rebuilds who holds the cut from the log itself.** The in-memory maps are lost in a crash; every namespace with a record at or above the durable cut starts out holding it (`safe_offset` = the cut, `last_write` = its last record's end), and `Database::open_vector_index_wal` releases namespaces no longer in the registry. Without the rebuild, the first flush of *any* namespace found nobody holding the cut and moved it to the tail, retiring records that exist only in replayed memtables — a second crash would lose them. Guards: `a_reopened_log_holds_the_cut_for_records_nobody_flushed`, `a_restart_keeps_the_cut_behind_records_nobody_flushed` (both fail without the rebuild; the second also fails if dropped namespaces are not released).
- The GC tick's vector pass (`perform_vector_wal_gc_check`) runs after the main pass and never reads its decisions: flush namespaces holding the cut, then delete segments wholly below it. **The pin flush seals even an empty memtable** (`KVStore::seal_and_flush_to_level0`): only a seal releases a holder, and a namespace can hold the cut with an empty memtable (a logged record whose apply failed twice is in no memtable). `flush_memtable_to_level0` skips an empty memtable, so a holder stayed forever. Guard: `a_pin_flush_releases_a_holder_whose_memtable_is_empty`.
- **The written event is fallible and vetoes the flush.** `LsmFlushObserver::on_ro_memtable_written` returns `io::Result`; on an error `flush_ro_memtable_to_level0` removes the written files, leaves the memtable read-only and unflushed, and returns the error (a later flush retries the same version). The vector index WAL computes the new progress, writes the marker, and only then commits in memory; on a marker error it undoes the namespace's tentative `safe` and its seal's `flushed` flag, so no later marker (written for another namespace) carries the failed flush. `SyncValueLogBeforePersist` returns the value-log fsync error the same way. Before this, a failed marker write only logged (files registered and mergeable with the marker behind), and a withheld event left that version's seal unflushed forever, wedging the namespace's progress. Guards: `a_failed_written_event_undoes_the_flush_and_a_retry_completes_it` (lsm_tree), `a_failed_marker_write_changes_nothing_and_the_retry_retires`, `a_flush_whose_marker_fails_registers_nothing_and_is_retried`.
- **A seal never takes `retirement`** (held across the marker's fsyncs). The hub calls `on_memtable_sealed` for every namespace under its memtable write lock, so waiting there stalled unrelated stores' reads and writes during vector marker writes. Seal records, `last_write` and the forgotten set live in `tracking` (held briefly, no I/O); the tail is an atomic published after the `in_flight` registration, so `ceiling` no longer takes `active` (held across rotation fsyncs). Lock order `retirement → tracking → in_flight`, `active → in_flight`. Guard: `a_seal_never_waits_for_a_marker_write`.
- **A forgotten namespace is never tracked again** (`Tracking::forgotten`; ids are not reused). `append` updated tracking after releasing the append lock, so a write racing `remove_namespace` re-added the dropped namespace with `safe = 0` and it held the cut until restart (its store is gone, so the pin flush skipped it). Guard: `an_append_after_a_namespace_is_forgotten_does_not_hold_the_cut`.
Stats: `Db::vector_index_wal_stats` → `GET /admin/storage/vector-index-wal`; counters under `vector_index_wal` in ops-metrics.

**Vector index WAL recovery rules (step 3).** `Database::recover_from_vector_index_wal` runs at open in both constructors, before main-WAL recovery and before observers are wired: raise `next_seq` above the log's last seq, then replay each record at its original seq (`replay_upsert`, or `replay_delete` for a delete record: `value_len` = `u32::MAX`, no value bytes; the format version is unchanged). Load-bearing:
- **Replay is per namespace.** A record is applied only at or above *its namespace's* durable `safe_offset` (the marker lists every tracked namespace whose offset is above the cut; others replay from the cut). Replaying from the global cut brought deleted keys back: the vector deletes are in the main WAL, so a flushed namespace's record above the cut could have a later delete already merged into L1, tombstone dropped. Repro and guard: `replay_does_not_bring_back_a_key_whose_delete_reached_l1` (written failing first; fails again with global-cut replay), plus `replay_skips_each_namespaces_records_below_its_own_safe_offset`.
- **Progress is durable before an L0 file is mergeable.** `flush_ro_memtable_to_level0` writes and fsyncs every bucket's file, fires `LsmFlushObserver::on_ro_memtable_written`, and only then registers them; the log retires and writes its marker in that event (value log fsynced first by `SyncValueLogBeforePersist`). The main WAL saves its progress in the same event (A1, *Main-WAL retirement* below). Guard: `the_written_event_comes_before_registration_and_in_version_order` (fails if the event moves after registration). Do not register an L0 file before that event.
- **A flush syncs the log before it writes any L0 file** (`LsmFlushObserver::on_ro_memtable_flushing`, the first flush event, → `VectorIndexWal::before_memtable_written`: a `sync` if the namespace has records past the durable tail, else no I/O; a failure vetoes the flush with nothing written). At open L0 files are found by listing the bucket directories, so an unregistered file still survives a crash; the sync must come before the write, not at the written event. This makes what survives any crash a **prefix of the log across namespaces**, which partition maintenance relies on to log its meta changes and key deletes (different namespaces) in program order. The trait method has **no default** on purpose: `SyncValueLogBeforePersist` wraps the hub, and a defaulted method it forgot to forward silently skipped the sync (caught by the test). Guard: `a_flush_syncs_the_log_so_a_crash_keeps_a_prefix` (fails on its crash assertion without the sync).
- **A marker past the durable tail starts a new segment at open.** A seal's ceiling can include unsynced appends; if their memtable was written, a power loss leaves the marker ahead of the log. New appends must land above every position it names, or replay would skip them. Guard: `a_marker_past_the_durable_tail_starts_a_new_segment`.
- **The crash simulation drops unsynced appends** (`mark_crashed` → `lose_unsynced`), so tests see a missing `sync`. Test helpers that model the worker must `sync` before "completing", as the worker will. Guard: `a_crash_loses_appends_that_were_never_synced`.
- **The write paths are `Database::put_ns_logged` and `delete_ns_logged`**: key stripe → seq → `append` (returns the `LoggedWrite` guard) → `put_to_storage_seq` with that seq (one retry) → drop the guard. It does not call `note_no_wal_write` (the write is recoverable) but does call `note_no_wal_index_exposure` (a field index on the namespace could not replay it from the main WAL). `Db`/`AsyncDb::sync_vector_index_wal` is the barrier.
- **A clean shutdown flushes with the observers attached, then detaches them and compacts** (`Database::shutdown`). It used to detach first: the last flush never reached the log, the marker stayed behind, and the shutdown's compaction dropped tombstones in L1, so the next open replayed records whose keys had been deleted — orphan chunk keys after any delete followed by a clean restart (found by step 6's partition tests: a key back in a retired posting). Guard: `a_clean_shutdown_does_not_bring_back_deleted_keys` (fails without the early flush). Only a compaction drops tombstones — and `KVStore`'s `Drop` compacts too (`flush_and_compact_all`), so detaching observers from a store that still holds unflushed data has the same hazard. A store whose flush fails at shutdown therefore **keeps its observers** (its shutdown's flush is observed, and vetoed if the marker still cannot be written); shutdown runs every step and returns the first error, and retires the main WAL (`retire_all`) only if every store shut down cleanly.
- **Recovery records what it replayed before main-WAL recovery runs.** No observer sees the replay, and `recover_from_wal` calls `flush_and_compact_all` on every store when it replays anything, which drops tombstones in L1 while the marker still lists the replayed records. Found by review 2026-10-17 and reproduced: put K (vector index WAL), delete K (main WAL), crash; open (K replayed, deleted, compacted; the main WAL retired past the delete); the compaction worker's `compact_due` removes the obsolete L0 file holding the tombstone (it runs for every store on any seal, `cleanup_obsolete_level0_files`); crash; open → K is back. It also left the namespace holding the cut with an empty memtable. Now `recover_from_vector_index_wal` flushes every namespace still holding the cut after replay, fsyncs its value log, and calls `VectorIndexWal::retire_replayed` (marker written; an error fails the open) — all before `recover_from_wal`. Guards: `a_second_crash_does_not_bring_back_a_deleted_key`, `a_restart_keeps_records_nobody_flushed` (fails without the open-time holder rebuild).
- Seq raise guard: `a_write_after_restart_beats_a_replayed_record`. Records of dropped namespaces are skipped and counted (`vector_wal_records_skipped`); a record failing twice goes to the fail log.

**Both write-size bounds must be checked before the WAL append.**
`Database::check_write_size` enforces two limits, and for a long time only the
first existed: the `u32` field widths (~4 GiB) *and* the value-log segment
capacity (`DbConfig::segment_size_bytes`, default 256 MiB — far tighter). A value
between the two passed validation, got a fsynced WAL entry so `put` returned
`Ok`, and only then hit `ValueLogError::ValueTooLarge` inside `ValueLog::append`
— past the durability barrier, where the write path treats failures as
best-effort. All three apply attempts failed identically (size does not change
between retries), reads kept returning the previous value, and WAL replay hit the
same error at every open. `crate::store::value_log::max_record_payload` is the
shared bound; keep it and `ValueLog::append` in agreement. Regression test:
`a_value_too_big_for_a_segment_is_rejected_before_the_wal`, which asserts the WAL
did not grow — that is what makes the rejection mean "nothing happened".

**Main-WAL retirement is saved progress, not entry statuses (built 2026-10-24, design `minnal_db/docs/Main-WAL-Rework-Design.md` A1).** The log is append-only: nothing writes into a frame after it is appended (`a_flush_retires_entries_without_writing_into_the_log`). `WalMetadata` holds `cut` and `safe` (namespaces whose safe offset is above the cut); recovery replays an entry only if `offset >= replay_from(ns)`, and WAL GC deletes segments wholly below `cut`, from the head up. Load-bearing:
- **Progress is saved on *written*, before L0 registration, and goes live only after the save** (`WalPersistObserver::prepare_written` → `PreparedProgress::commit`). Saved on *flushed* (after registration), compaction could merge the files before the save, and a main-WAL put could replay after a vector-index-WAL delete of the key reached L1.
- **The hub saves the main WAL first and commits it only after the vector index WAL's event succeeds** (`LsmFlushObserverHub::on_ro_memtable_written`). An observer error undoes the flush and *deletes* its L0 files, so progress made live before that would claim entries are in deleted files. On the vector WAL's failure, `PreparedProgress::abort` re-saves the previous metadata; if that fails too, the main WAL is poisoned (`KVError::WalPoisoned`, writes refused until reopen). Guards: `a_vector_wal_failure_after_the_main_save_puts_the_main_progress_back`, `a_failed_rollback_stops_the_main_wal`, `a_failed_progress_save_undoes_the_flush_and_a_retry_completes_it`.
- **Every metadata save goes through `persist_lock`** (`save_metadata`, `retire_all`, progress saves), so two saves cannot land out of order; none holds the WAL lock across I/O. Guard: `concurrent_flushes_leave_the_saved_progress_equal_to_the_live_one`.
- **Recovery retires the whole log only if every replayed namespace flushed** (`retire_all`); shutdown likewise.

**A tail snapshot over-states durability — never derive the cut from `wal_metadata.tail` alone.** The cut may pass a WAL entry only once its key is in an SSTable, because recovery *skips* entries below it. But `put_ns`/`delete_ns` append under the WAL lock and apply to the memtable **after** releasing it, so in between an entry is visible in the tail while its key is nowhere. Two readers used the raw tail and both lost acknowledged writes:

| Reader | What it did | Why it was wrong |
|---|---|---|
| `try_advance_persisted` (now `compute_cut`) | cut at the live tail whenever no namespace reported un-flushed writes | includes the in-flight entry |
| `on_memtable_sealed_ns` | recorded the live tail as "everything below this is in the memtable I am sealing" | an in-flight write's apply lands in the **next** memtable, while its offset sits below the recorded tail — so `advance_namespace` pushed `safe_offset` past an entry no SSTable held |
| `run_index_checkpoint` | recorded the live tail as the offset every field index (and the row map) reflects | an in-flight write's index update happens after its WAL append, so the tail could include it; after a crash, replay started past it and the document stayed out of every field index, with no gap recorded. Found by the SIGKILL stress harness (1–2 documents per crash at a 300 ms checkpoint interval); regression test `index_checkpoint_stops_below_an_in_flight_write` |

All three now go through **`WalPersistObserver::wal_cut_ceiling()`** = `min(tail, lowest in-flight offset)`. `put_ns`/`delete_ns` register the entry's start offset with `begin_write()` **while still holding the WAL metadata write lock** — that ordering is the entire guarantee: no observer can see a tail containing an entry without also seeing that it is not yet applied. The returned `InFlightWrite` is RAII because a leaked registration pins the ceiling forever, freezing the cut so WAL GC never reclaims again (the `17a8a0c` failure mode, reached another way), and `put_ns` has fallible steps between the append and the apply.

The registry is **refcounted** (`BTreeMap<u64, u32>`), not a set: an entry starts exactly where the previous tail ended, so a synthetic registration at a tail offset collides with the next real append and a plain set lets one `Drop` cancel the other's protection.

Note the cut's cap is *redundant by argument* — because registration happens under the WAL lock, no seal can overtake an in-flight write, so `safe_offset` already stays behind the barrier. It is kept because that argument is non-local (it lives in `put_ns`, far from the `None` branch it protects) and pinned by its own test, so moving the registration out of the WAL lock cannot silently re-open the hole.

Measured before the fix (2026-08-02 stress run): **1 acknowledged write lost in 34,538**, and 4 lost in one round of `work/stress/repro/drop_loses_a_write.py`. A namespace drop is the trigger, because `forget_namespace` calls `try_advance_persisted()` the instant it removes a namespace — precisely when the set of namespaces reporting un-flushed writes can go empty while a survivor is mid-write. The tell-tale is that **recovery does not run at all** after the crash (`persisted == total` short-circuits it). Regression tests: `an_in_flight_write_holds_the_persisted_watermark_back`, `a_memtable_seal_does_not_claim_an_unapplied_write`, `the_cut_respects_the_barrier_even_when_no_seal_enforces_it`, `dropping_a_store_does_not_persist_a_survivors_in_flight_write`, `the_in_flight_barrier_is_released_when_the_write_finishes`.

**Known remaining hole (pre-existing, not this bug):** if `apply_with_retry` exhausts its retries, `put_ns` still returns `Ok` and the barrier is released, so the cut can pass that entry and recovery skips it. It is ERROR-logged and written to the fail log, which is the operator's recovery path.

**WAL GC is gated on the index-replay watermark — do not reclaim a segment on the cut alone.** The field index is made durable by an inline in-memory update per write plus a periodic checkpoint recording the WAL offset it reflects; a crash is healed by replaying from that offset. Reclaiming on LSM persistence alone deleted the WAL that heals it, and the affected documents were then absent from the index **for the life of the database**, with queries silently returning incomplete results (measured: 10 segments reclaimed, 15 of ~360 writes still replayable). `garbage_collect_wal` now consults `index_replay_watermark_segment` = `min(checkpoint offset)` over **currently active** fields, via the shared `plan_wal_gc` that `has_deletable_wal_segments` also uses — keep those two agreeing or the worker either spins on segments GC refuses or skips the pass meant to fire the backstop. **The offsets are event-driven, not read from markers (A2, 2026-10-24):** `WalPersistObserver::field_consumers` holds each active field's position, added in `activate_field_index` (from its marker: `At(p)` → `Some(p)`, `Absent` → `None` = holds from 0 only once populated, `Unusable` → `Some(0)`), moved by `fields_checkpointed` only *after* `checkpoint_fields` made the markers durable, removed in `deactivate_field_index`, `drop_field_index` and `forget_namespace`. A consumer never removed pins the WAL for good. Guards: `a_checkpoint_whose_marker_fails_does_not_move_the_position`, `deactivating_or_dropping_a_field_stops_it_holding_the_wal`, `dropping_a_namespace_stops_its_fields_holding_the_wal`, `a_field_without_a_checkpoint_holds_the_wal_only_once_populated`.

Three properties are load-bearing:
- **Active fields only.** A dropped field's marker is frozen and a first-time build has none (reading as "replay from 0"); either would pin the WAL without bound. The empty + `CheckpointState::Absent` case is suppressed exactly as `detect_replay_gap` suppresses it — a new index is populated by a *build*, not by replay.
- **Liveness via the checkpoint trigger.** When segments are pinned, GC fires `IndexCheckpointTrigger::request()` (uncapped — `request_if_over_cap` returns early when the backpressure valve is disabled) so retention tracks checkpoint latency, not the periodic timer.
- **The backstop produces gaps by design.** Past `thresholds.max_pinned_wal_segments` GC reclaims the oldest pinned segments anyway and logs an ERROR. This is why detection and repair (FR-001 steps 3–5) are still required: prevention makes the condition rare, not impossible.

**Queries return `QueryOutcome`, not a bare `Vec` — do not "simplify" it back.** `query_keys` / `query_keys_paginated` (facade `Db::query_index` / `query_index_paginated`) return `{ keys, total, degraded_fields, touched_fields }`. A degraded index stays *queryable*, so handing back a complete-looking `Vec` over one is the original silent-wrong-answer bug re-triggered by repair instead of GC. The touched-field set comes from the evaluator itself — `evaluate_predicate` records every `field_id` the index-lookup closure is asked for — so it is exact and needs no second parse, and only fields *this* predicate referenced can mark it degraded. It also carries `touched_fields`; the doc store adds any touched field whose `build_progress.json` is `in_progress` or `failed` (a building index holds only the documents the build reached). Carried through `doc_store` into `Page::degraded_fields` (names, not ids) and out as `degraded_fields` in the `POST /stores/{ns}/query` and filtered-semantic-search JSON. The empty-result case is the one that matters most: without the flag, "nothing matched" and "the rows are missing" are indistinguishable.

**Repair is row-scoped, and `reindex_field` must clear the row of an absent key.** `Database::repair_field_index` reads the gap record and either walks its key worklist or rebuilds the field, then checkpoints **before** clearing the gap (the reverse could lose the repair to a crash and leave nothing saying so). It reads each key's *current* value, which is what makes repair idempotent and convergent. Note `KVStore::reindex_field` removes the row when the key has no value: the lost update can be the **delete**, and leaving the stale row would make the index wrong in the other direction — it returns `KeyNotFound` to describe what it found, not to say it did nothing. Surfaced as `POST /admin/indices/{ns}/attribute/{field}/repair` and `GET /admin/indices/{ns}/health`. **Every reindex outside the write path goes through `Database::reindex_key`, which holds the key stripe** — the facade's `reindex_field`, both repair modes, and the doc-store index build. Reindexing reads the current value and then sets the row; the write path updates the index after its apply under the stripe, so an unlocked reindex could read v1, let a put move the row to v2, then set it back to v1. **A full rebuild also sweeps orphan rows**: after walking live keys it visits every row the index holds that no live key accounts for and reindexes its key (`KVStore::key_for_row`), which clears the row of a key that no longer exists — walking live keys alone never could. Regression test: `test_full_rebuild_clears_the_row_of_a_key_that_no_longer_exists`.

**A new index (`DocStore::add_index`) is populated by reindexing, never by re-putting documents.** Activation replays only the WAL still retained, so the background build must index every existing document itself. It used to re-put each document's scanned bytes, which (a) is a no-op for the index when nothing changed — `DynFieldIndex::update` skips `old == new` — so on a store whose WAL had been reclaimed it indexed 28 of 300 documents and reported success, and (b) wrote back bytes read a page earlier, overwriting any newer write to the key. It now calls `Db::reindex_field` per key: no WAL traffic, no document rewrite. Regression test: `test_add_index_covers_documents_whose_wal_was_reclaimed`.

**Gap records: the index reports its own incompleteness.** A field index that is missing updates writes a durable `gap.json` beside its `checkpoint` marker (`IndexManager::read_gap`/`record_gap`/`clear_gap`), carrying a `GapCause`, the WAL range, and a `RepairMode` — either a row-scoped worklist of hex-encoded keys or `FullRebuild`. Records **merge** rather than overwrite (a second detection must not discard the first worklist), and `FullRebuild` is absorbing. Three causes feed it, and the second and third are *not* WAL-GC problems — they are separate ways the index diverges from the store, each invisible to `detect_replay_gap`:

| Cause | Detected | Repair | Why it can't be caught later |
|---|---|---|---|
| `BackstopReclaim` | inside `garbage_collect_wal`, **before** the unlink | row-scoped | the affected keys live only in the segments being deleted |
| `NoWalWrites` | at open, from a durable per-namespace marker | full rebuild | no WAL entries ever existed, so the keys were never knowable |
| `RejectedUpdate` | write path → buffered → persisted at checkpoint | row-scoped | — (key is known exactly; buffering just avoids an fsync per write) |

**Main-WAL scans all go through `Wal::walk` → `SegmentedLog::for_each`**, and must stay that way. A body that passes its CRC but does not decode as a `WalEntry` is corruption (`undecodable`), never a torn tail (`an_undecodable_entry_is_corruption`); a changed byte inside a value still decodes under rkyv's validation, which is why the CRC exists (`a_changed_byte_in_a_value_is_caught_by_the_crc`). Three scans sit on it — `scan_entries` (full entries), `scan_keys_in_entries` (key-only over a range, no values materialised), and `scan_segment_keys` (one segment, deduplicated — the harvest that makes row-scoped repair possible; an already reclaimed segment yields nothing). Pinned by `key_only_scan_agrees_with_the_full_scan`, which checks the key-only and full scans agree, including below reclaimed segments. **Segments are zero-filled ahead** (design note §15, §17): sparse alone saves only the size update — a write starting a new 4 KiB block still commits its allocation (2 KiB writes 1.5 ms, 8 KiB 2.3 ms); zero-filled holds ~0.73 ms at every size. An entry too large for a segment is refused before anything is written and reported as `KVError::WriteTooLarge` (`a_write_too_large_for_a_wal_segment_is_refused`); `check_write_size` bounds only the value log, since the WAL's exact bound is the serialised entry.

**The no-WAL marker is written before the write it describes.** Marker-then-write can only produce a spurious gap (a full rebuild is idempotent); write-then-marker can lose both and leave the index silently incomplete. It is debounced by an in-memory set to one fsync per checkpoint interval, and `Database::shutdown` checkpoints first — which is what makes a surviving marker mean "unclean shutdown".

Dropping a field index goes through `Database::drop_field_index`, which **persists the `dropped` flag first**, then deregisters, then deletes `index/{ns_id}/{field_id}/`. A crash leaves the drop recorded so `complete_interrupted_field_drops` finishes it at open. The reverse order leaves a registered field with no data, which reads as `Absent` + empty and is *suppressed* as a normal first build — a silently incomplete index. `deactivate_field_index` remains deregister-only and does not touch disk.

## Public API surface

`Db` / `AsyncDb` (facade) with namespaces are the only entry points. `Namespace` is the scoped per-namespace handle returned by `Db::namespace()`.

CRUD is `put` / `get` / `delete` / `merge`, each with a `_typed` (rkyv) twin, on all
four surfaces. **`merge` is the one write that reports a failed in-memory apply**
(`KVError::MergeNotApplied`) instead of returning `Ok` like `put`/`delete` do —
its result never became readable, so the next merge on that key would accumulate
onto a stale base. The write is still durable and replays on the next open; the
error means "not readable yet", not "lost". The converse is undetectable: a merge
reading a key whose last `put` is stuck in that window gets the stale value with
no way to tell. `merge(key, value, closure)` is the atomic read-modify-write; the
closure returns `Ok(Some(v))` to write, `Ok(None)` to delete (writing nothing when
the key was already absent), or `Err` to abort — `KVError::MergeAborted` exists so
declining does not have to borrow a variant that means something else. It runs
while the key stripe is held, so it must not call back into the `Db`. Library only:
there is no REST or doc-store merge, because a Rust closure does not cross an HTTP
boundary.

**Where does a new operation go?** Four entry types with overlapping surfaces (`Db`, `Namespace`, `AsyncDb`, `AsyncNamespace`) means every operation exists at least twice, and the sync/async split is inherent to offering both. The rule, so the split stops drifting: an operation goes on **`Namespace`** if it acts on one namespace's keys or its indices, and on **`Db`** if it spans namespaces, touches the shared WAL, or is engine-wide (stats, GC, compaction, worker control). Async mirrors sync exactly — never add to one side only. A 2026-08-01 review found this choice looked arbitrary from outside because it had never been written down; that was the whole problem.

There is **one** async wrapper. A second (`AsyncDatabase`) existed for a long time with no callers but its own tests, and its independent worker-management copy silently diverged — `AsyncDb::shutdown` never stopped the index checkpoint worker, and nothing noticed because the dead wrapper did. Deleted in `cef37d9`; don't reintroduce a parallel surface.

`Database`, `AsyncDatabase`, and `KVStore` are **internal** types: `Database`/`AsyncDatabase` is the coordinator behind `Db`/`AsyncDb`; `KVStore` is the per-namespace store behind `Namespace`. They are no longer re-exported from the crate root (the deprecated `pub use` aliases were removed). Refer to them only via internal paths (`crate::db::database::Database`, `crate::db::kv_store::KVStore`).

`MinnalStore` / `AsyncMinnalStore` have been removed entirely. `src/db/db.rs` now holds only integration tests for the facade.
