# semantic_search — Vector Quantisation + ANN Search

Implements IVF (Inverted File Index) clustering with RaBitQ quantisation for two-pass approximate nearest-neighbour search over dense embeddings. Vectors are stored in `minnal_db`; this crate handles quantisation, cluster assignment, and search.

## How it works

### Chunking (done here, not by the service)

The embedding service no longer chunks text — `src/chunking/mod.rs` does. **Only documents are chunked**: `chunk_document` splits on **sentence** boundaries and groups the sentences into overlapping **sliding windows** (`window_size` sentences per window, advancing `sliding_size`; the last window keeps the remainder), each joined into one payload string. **Queries are not chunked** — one whole-query embedding serves both passes (see *Search* below). The service receives a list of already-prepared payloads and returns one embedding per payload.

### Indexing (dual quantisation)

Each document goes through a **single** embedding service call (`embed_document`) that embeds one ordered payload list — `[whole_text, chunk₀, chunk₁, …]` — and splits the (order-preserving) response by position:

1. **MultiBit (dense)** — `payload[0]`, one embedding for the whole document text, quantised to `number_of_bits_for_dense_quantisation` bits per dimension. Stored in `{ns}_dense_vector` keyed by `doc_id`. Used for high-precision re-ranking in Pass 2.
2. **SingleBit (sparse, sliding-window)** — `payload[1..]`, `chunk_document`'s N sliding-window chunks → N embeddings. Each chunk is independently assigned to its nearest IVF cluster and quantised to 1 bit per dimension. Stored in `{ns}_sparse_vector` under composite keys `[cluster_id (4B BE) ‖ doc_id]`. Used for fast first-pass cluster scans.

Folding both into one call is one round trip and one GPU batch of `N+1` (the service preserves payload order, so position 0 is always the dense vector). The query path (`embed_query`) sends a single payload: the whole query.

A third namespace, `{ns}_sparse_vector_meta`, is each document's index record: `text_hash (8B) ‖ count (2B) ‖ cluster_ids`. The cluster list is the only way delete and upsert cleanup find the document's chunk keys again; the text hash (`vector_kv::text_hash`, FNV-1a, pinned by `text_hash_is_stable`) records which text the vectors came from. It is written for every indexed document, including one with no chunks.

**Durability split (vector-WAL payloads, WAL-backed meta and deletes).** The vector **payloads** — `{ns}_sparse_vector` and `{ns}_dense_vector` — skip the main WAL: `vector_kv::upsert_vectors` writes them with `put_logged`, which appends them to the separate **vector index WAL** (`db/vector_index_wal.rs`, no per-write fsync) and applies them under the key stripe with the logged seq. They are bulky and reconstructable by re-embedding, so a per-chunk main-WAL fsync plus a second copy there is pure overhead; one fsync of the vector index WAL per completion batch makes them durable instead, and after a crash unretired records are replayed (per namespace, from its durable safe offset — `minnal_db/CLAUDE.md` → *Vector index WAL recovery rules*). A crash before that sync can still lose a just-indexed vector; the entry was not completed, so the queue (M0-1 below) redoes it. These writes are not flagged as no-WAL (`note_no_wal_write`): they are recoverable, so the compaction worker's no-WAL flush tick leaves them alone (`test_vector_writes_go_to_the_vector_index_wal`). Partition maintenance logs **all** its per-document writes the same way — the copies and the destination's meta (`ivf_split::copy_into_batch`), the drained posting's meta drop and key delete (`drain_delete`), and reassign's source meta and key shrink (`reassign::shrink_sources`, `delete_logged` when a key empties) — with **one sync per batch, before the batch releases its documents' vector locks** (`ivf_split::sync_batch`). This is safe only because of the log's prefix rule: a flush syncs the log before writing L0 files (`LsmFlushObserver::on_ro_memtable_flushing` → `VectorIndexWal::before_memtable_written`), so what survives any crash is a prefix of the log across namespaces, and maintenance's meta-before-key orders hold. Don't make maintenance's writes no-WAL instead: the meta and the keys flush independently, and a kept key delete with a lost meta drop is the stranded meta `drain_delete` warns about (mutation check: logging the key delete first fails all three crash audits). A split now costs the main WAL only its own records, not ~3 fsyncs per moved document (`a_split_writes_nothing_per_document_to_the_main_wal`; `report/Fewer-WAL-Fsyncs-Design.md`, Part 2). The partition's own records (centres, postings, journal, including `init_ivf`'s root and the test-only `seed_ivf`) are WAL-backed puts, durable on return; no vector-index write uses `put_no_wal` any more (only the query-embedding cache does, and the embed queue's completions use `merge_no_wal` — see below).

**The meta is WAL-backed and written between the stale deletes and the new keys — do not move it.** `upsert_vectors` goes: (1) delete stale cluster keys (WAL), (2) put the new meta (WAL, durable on return), (3) put the chunk keys and the dense entry (vector index WAL, durable at the batch's sync). The meta must list every key that can be on disk at every moment, and each namespace's memtable flushes on its own schedule (size-triggered), so a no-WAL meta could be lost while a key written after it was flushed: a later delete then misses the key for good, and a reused document id inherits it. One fsync per document upsert, negligible beside the embedding call. Crash-audit test: `delete_racing_a_reembed_survives_a_crash_anywhere`.

**Queue first, then the document; the worker checks each entry against the document (no reconciliation scan).** A document write and its embed enqueue are separate writes, so every writer (`DocStore::put` / `put_no_wal` / `delete`, `kv_put_inner` / `kv_delete`) writes the **queue entry first** (`enqueue_embed`, or `clear_vectors`' `Clear` tombstone) and the document second, holding an `InFlightWrite` (`DocStore::begin_vector_write`, `store/types.rs`) from before the first write until the second returns. A crash between them leaves an entry that does not describe the document, never a changed document with nothing queued. Before acting on any entry the worker calls `vec_index_worker::check_entry`: if a write to the document is in progress it **skips** the entry (`Processed::InProgress`; the guard's drop wakes the worker, and a pass that only skipped returns instead of spinning); otherwise it reads the document's embedding text (`doc_store::store::document_text`) and calls `vector_kv::check_entry_against_document`: an `Embed` must carry the document's text, a `Clear` needs an absent or empty-text document; otherwise the entry is rewritten (conditional `merge`, fresh retry count) to the document's state and done next pass. **The in-progress skip is load-bearing**: without it the worker could read the document between a writer's two writes and rewrite the writer's new entry back to the old text, or (the race that killed the run-number idea) embed a reindex's stale snapshot after completing a writer's entry but before the writer's document write landed. Both race tests fail with the skip removed (`a_stale_entry_waits_for_a_write_in_progress`, `the_worker_skips_a_document_with_a_write_in_progress`). **`InFlightWrites` must never block anyone**: it replaced a striped per-document `lock_doc_write` (user decision 2026-10-26, the lock made writes wait on each other and on maintenance). It is a refcounted `HashMap<u64, u32>` of hashed (store, key) under a `parking_lot` mutex held for a map update only; ~16 bytes per write in progress. The guard must stay RAII (a leak would skip the document for good; `a_write_in_progress_is_forgotten_however_it_ends` cancels a write mid-await). The check runs first in `process_one`, before the namespace's settings are resolved. Reindex (`index_all` / `kv_index_all`, one body `reindex_vectors`, paged 1,000 rows; single-doc reindexes) enqueues plainly from its snapshot and takes no guard: the check corrects stale text. This replaced startup/on-demand reconciliation (removed 2026-10-26): it read every document of every semantic store (`ns.iter()`, whole namespace in memory) with ~4 point reads each, never finished on a large corpus, ran detached from shutdown so the closing database made it log an ERROR, and `POST /admin/indices/vector/reconcile` went with it. Don't bring back a corpus scan: recovery must stay proportional to the queue. The meta's text hash is still written (on-disk format) but nothing reads it for recovery. Crash audit: every scenario fails with the entry check disabled (mutation-checked); unit tests `an_entry_is_rewritten_to_what_the_document_holds`, `a_newer_entry_is_never_rewritten`, `an_entry_for_a_missing_document_becomes_a_clear`; through the worker: `a_delete_cut_short_by_a_crash_is_redone_as_an_embed`, `an_upsert_cut_short_by_a_crash_embeds_what_the_store_holds`. Corrupt vectors (counted by `metrics/corruption.rs`) are repaired by `reindex-all` on the store.

**Foreground deletes stay WAL-backed.** The worker's and the document delete's cleanup **deletes** stay **WAL-backed** — the stale-cluster deletes on upsert and the full reverse-lookup `delete_vector` (reads `{ns}_sparse_vector_meta` to delete every composite key, then the dense entry). They are tiny key-only tombstones, and unlike a lost write a lost delete is *not* self-healing: a lost delete leaves an *orphan* composite key that no meta lists and a re-embed never revisits. (Maintenance's deletes are logged instead: its journal redoes a step from the posting's own keys, so a delete lost with the rest of its unsynced batch is redone.)

**A queue entry is completed only after its vectors are durable — do not complete first.** The payload writes above are durable only at the vector index WAL's next sync, but the stale-key deletes are WAL-backed and durable at once, and the queue completion (`complete_entry`, a `merge_no_wal`) can reach disk at any moment with the queue's next flush. Completing first let a crash keep the completion and the deletes while losing the new vectors: a re-embedded document kept its *old* dense entry with nothing queued to replace it (stale vectors for good, minus its moved chunks). The worker writes (`upsert_vectors`), collects up to `COMPLETION_BATCH` (256) written entries, makes them durable with **one fsync of the vector index WAL** for the whole batch, however many stores it spans (`vector_kv::make_vector_writes_durable` → `AsyncDb::sync_vector_index_wal`), and only then completes them (`complete_embed`); a failed sync completes nothing. A failed fsync also **stops the vector index WAL until the database is reopened** (`VectorIndexWalError::Poisoned`, see `minnal_db/CLAUDE.md`): every later `put_logged` and sync fails, so indexing stops loudly and entries stay queued, rather than completing later batches over pages the kernel may have dropped. `finish_embed` is the same three steps for one entry. The barrier used to be a flush of the three vector namespaces per batch — at low load one document per batch, ~20 memtable flushes a second in the M5 benchmark (design doc §1). Regression tests: `crash_before_reembed_is_synced_keeps_new_vectors` (fails without the sync, since `AsyncDb::crash` drops unsynced appends), `a_failed_sync_completes_nothing`, `crash_after_flush_before_completion_redoes_the_entry`, `records_of_a_sealed_but_unwritten_memtable_replay_after_a_crash` (fails if records retire at the seal).

**Queue completions skip the WAL (`merge_no_wal`) — keep them after the sync.** A completion only records "done"; lost to a crash, the entry comes back and the document is embedded again with the same text, which is harmless. As a WAL-backed `merge` it cost one main-WAL fsync per document on the lock every REST write takes. It stays a conditional merge under the key stripe (R1–R3 unchanged), and replay can never bring an older entry back over it once flushed: the older put replays with its lower seq and loses to the tombstone in L0 (`a_replayed_older_put_loses_to_a_flushed_no_wal_delete`). A crash costs at most one LSM tick of re-embedding. Retry counts (`record_queue_failure`), `Clear` tombstones and the worker's rewrites (`check_entry_against_document`) stay WAL-backed. Tests: `crash_replays_completion_and_failure_results`, `a_lost_completion_never_hides_a_newer_upsert`, both flush cases of `crash_before_reembed_is_synced_keeps_new_vectors` (`report/Fewer-WAL-Fsyncs-Design.md`, Part 1).

**One document's vector writes are serialised (`vector_kv::lock_doc_vectors`).** `upsert_vectors` and `delete_vector` are multi-key read-modify-writes whose only index of the sparse keys is the cluster list in `{ns}_sparse_vector_meta`, and they run concurrently whenever a document delete races the vector worker. Interleaved, a delete read the old list and then deleted the list the upsert had just written, leaving the upsert's new cluster keys orphaned for good (measured 260 in 300 racing rounds). Both now hold a striped per-`(namespace, doc)` async lock across their whole body; the process owns the database exclusively (directory lock), so in-process locking is enough. Don't call one from inside the other while holding it. Regression test: `racing_upsert_and_delete_leave_no_orphaned_cluster_keys`.

**An interrupted vector-index drop is finished at open (`DocStore::finish_interrupted_vector_index_drops`).** Dropping saves the schema with semantic search off, then clears the queue and removes the vector namespaces in the background; a crash in between left both, and the worker would process the leftover entries and recreate the namespaces. At open, before any worker starts, every namespace with vector data or queue entries but no semantic-search schema gets `drop_vector_index_data`. Test: `an_interrupted_vector_index_drop_is_finished_at_open`.

**Reindex records report progress; they do not block.** A `vector_reindex.json` record used to stay `"running"` for good (nothing ever wrote `"complete"`), so every later `reindex-all` was refused with 409. Now concurrency is an in-memory claim per namespace held only while `index_all` / `kv_index_all` enqueues (`ReindexClaim`), and `vec_reindex_progress` (async) brings a `"running"` record up to date as it reads it: `"complete"` once `enqueue_done` and none of the namespace's work is queued, `"failed"` if the enqueue never finished and no claim is held (a crash cut it short). Tests: `a_finished_reindex_does_not_block_the_next`, `a_reindex_interrupted_by_a_crash_does_not_block_the_next`.

**Crash audit (design doc M0-2).** `vector_kv::crash_audit_tests` runs each write path with a simulated crash before every write (`crash_point!()`, a test-only countdown before each vector-index write in `vector_kv`), under five flush patterns (no namespace, each one alone, all), then restarts in production's order (the worker draining the queue, each entry checked against its document) and checks that the vector index matches what the store holds. Add a `crash_point!()` before any new vector-index write, and a scenario for any new multi-step path.

The **query-embedding cache** (`system_qemb_cache`, below) follows the same split. Populates are no-WAL (`put_no_wal`): the cache is TTL-bounded and fully regenerable from the embedding service, so a dropped populate is just a future miss, and staying off the WAL removes a per-populate fsync from the query hot path. The admin clear (`DELETE /admin/indices/vector/query-cache`) deletes **WAL-backed**: the periodic no-WAL flush tick has usually already persisted the entries being cleared, so a no-WAL tombstone lost to a crash before the next tick would resurrect them — serving entries the operator explicitly cleared until the TTL expires. The clear is a rare admin operation, so the per-delete fsync is off the query path.

### Rotation (codes live in a rotated space)

Each namespace has its own rotation: the seed is recorded in its schema (`vector_index.quantisation.rotation_seed`, read-only, default `DEFAULT_ROTATION_SEED`) and its `NamespaceIvf` rotates its centres and queries with it. A `ClusterIndex` holds one `FhtKacRotator` and a rotated copy of every centroid. Indexing (`index_embedding_rotated`) picks the nearest cluster on the **original** vector, then quantises `Pᵀx` against `Pᵀc`; `search()` rotates each query once and uses the rotated query for every term that meets a code (the query sum, `scaled_query_sum`, and the packed dot products), while cluster probing and `⟨q, c⟩` use the original (rotation preserves both). **Mixing the two spaces is the bug to watch for**: a rotated code scored with an unrotated query sum, or the reverse. `rotated_scoring_matches_scoring_fully_rotated_inputs` checks the formula wiring, and `rotated_index_finds_the_source_document_end_to_end` (with a first-pass cut of 3, so Pass 1 must rank correctly too) fails if either pass's query is left unrotated. Dimensions that are odd or below 8 get no rotation (only tiny test indexes); the API rejects such an `embedding_dim`. Its effect depends on how evenly a model's residuals spread over dimensions. Gemma (already even): estimator RMSE −0.6% / −2.2% (SciFact / FiQA), nothing else changes. Qwen (concentrated): without rotation the 1-bit estimate is biased (−0.0105 / −0.0035); rotation removes that, cuts RMSE 11–15% and adds 1.2–1.4 points of Pass-1 recall. nDCG@10 and latency are unchanged on both (design doc M1, `report/rabitq-rotation-audit.md`).

### Search (two-pass ANN)

`embed_query` makes **one** embedding of the whole query (one payload, one service call) and uses it for **both** passes: as Pass 2's dense vector and as Pass 1's single MaxSim query vector (`QueryEmbeddings { sparse: vec![dense.clone()], dense }`). Queries used to be split into 4-word sliding windows; a BEIR evaluation (`report/query-embedding-report.md`) found the whole-query vector never worse and often better. With a tight first-pass cut it kept more relevant docs (ArguAna candidate recall 0.991 vs 0.870). It is also far cheaper: one embedding instead of 1+N, and `n_probes` clusters instead of the union over every fragment (up to 74% faster search). Document-style sentence windows for long queries gained nothing either, so there is **no query-chunking option**. `search()` still accepts several Pass-1 query vectors (general MaxSim) and returns empty if either input is empty. The embedding is cached in the `system_qemb_cache` TTL namespace, keyed by `model ‖ 0x00 ‖ dim (u32 BE) ‖ query text` (`vector_kv::query_cache_key`; `query_embedding_cache_ttl_secs`, default 1 day). Model and dimension are in the key because each namespace picks its own and one service serves several models: keyed by text alone, namespaces with different models (or the same model at two dimensions) would share query vectors. Since queries are not chunked, chunking settings never invalidate it either; clear it (`DELETE /admin/indices/vector/query-cache`) only if the service changes what it serves under the same model name.

**Pass 1 — sparse (SingleBit), ColBERT MaxSim over document chunks:**
1. Use the Pass-1 query vector (the whole-query embedding; fetched from the `system_qemb_cache` TTL namespace on a hit).
2. Find its `max_probes` nearest clusters by Euclidean distance (every active posting when there are fewer; `min_probes` is a floor for overrides; `cluster::select_probes`, per query vector, then the union). **No entry budget** (removed 2026-10-19, user decision): it walked postings until their entry counts reached `probe_budget_entries`, which users found unintuitive; postings are size-bounded by split and merge, so a posting count already bounds the read. Don't reintroduce a budget or a hidden share of postings without asking. Entry and chunk counts live in a `CountTable` shared by every snapshot of a namespace's partition: counted at load from the document records (`{ns}_sparse_vector_meta`, which since M3a record each posting's chunk count; read a page at a time), then kept current by the `PostingDelta` every vector write returns (`(posting, chunks)` per entry written or deleted). They are **exact** as far as the meta goes: nothing writes a namespace's vectors before its partition is loaded (every writer goes through `for_namespace`), and the split executor applies its own deltas. The split trigger depends on it; search only reports the planned entries. `ClusterIndex` has no counts (`posting_entries` = `None`, counted as 0), so raw `vector_kv` users, tests and the criterion benches use `ProbeSettings::fixed(n)` (exactly n probes, the old behaviour). This is an **exact, exhaustive** scan — `ClusterIndex::find_top_n_cluster_ids_batch` computes the distance to *every* centroid (over a contiguous centroid matrix) and selects the `n_probes` nearest (`select_nth_unstable`, ~O(C)). There is **no neighbour graph / approximate traversal**: coarse-assignment cost is **T·C·D** (query vectors × centroids × dim), and production `T = 1`, so it is ~microseconds at C≈256. A graph is the wrong lever — approximate on the most recall-sensitive stage, marginal at a few hundred nodes. The contiguous-matrix scan was a measured ~12% win back when queries were chunked (T up to 100); **parallelising the per-vector scans was tried and reverted (~2.4× slower — the work is microseconds, so the thread pool costs more than it saves)**; a blocked GEMM is the only remaining lever and only pays at far larger C. See `report/Semantic-Search-Architecture.md`.
3. `scan_sparse_clusters_batch(probe_clusters)` fetches every probed cluster in **one** call: `LSMTree::scan_prefixes` reads each LSM layer once for the whole prefix set (L1 seeks per prefix via the sparse index), then the value log resolves each pointer with its own `pread`. This scan is most of a warm query's cost and scales with the number of entries probed. **The result is packed** (`SparseScan` over `PrefixScan`): the LSM writes each L1 bucket's keys into one buffer and the output keys into another, and each value-log bucket thread reads its values into one buffer — no allocation per entry. Each entry used to cost four (L1 key copy, read buffer, value copy, doc-id copy), and dropping ~90k entries took ~6 ms, so it was handed to `spawn_blocking`; under 16 clients glibc malloc spent 14–16% of CPU in the allocator, mostly on this path, and mimalloc paid for the cross-thread frees. With the packed result (01ea124, 2026-10-18) the allocator's own code fell to 1.7% (glibc) and 1.1% (jemalloc) of CPU, and search p50 at 16 clients went 51 → 33 ms (glibc) and 30 → 23 ms (jemalloc). Keep new per-entry data in these buffers.
4. Take a `SCORING_GATE` permit (see *Concurrency* below).
   Then build one `SingleBitQuanDotProductEstimator` per (probed cluster, query vector). Each query vector's sum is computed **once** (`query_sum`) and passed to `with_query_sum`; recomputing it per cluster was 2.9 ms of a 6.0 ms search at 40 query vectors, because this pre-pass is single-threaded (it was not when estimators were built inside the old per-cluster fold).
5. Flatten every probed entry into one list and score it **in parallel over entries, not clusters** (IVF clusters are skewed; one can hold a third of a corpus), each entry into its own row of a flat `n_query`-wide matrix. Entries are read zero-copy from their rkyv archive. The optional `doc_filter` (RoaringBitmap predicate) skips non-matching docs here, as do corrupt or wrong-style entries.
6. Group per document with **ColBERT MaxSim**: sort the kept entry indices by `doc_id`, and fold each run of one document's entries (a document's chunks can sit in several probed clusters) with an element-wise max. `S(q, d) = Σ_i max_j ⟨q_i, d_j⟩`; with production's single whole-query vector this is `max_j ⟨q, d_j⟩`, the document's best-matching chunk. The sort replaced a per-document `HashMap` whose allocations and cross-thread merge were half of a FiQA query.
7. Keep the top `first_pass_sparse_search_top_k` with `select_nth_unstable` — O(n), because Pass 2 re-ranks and does not care about their order.
8. Release the permit and drop the scanned entries (a few buffers, so a few frees).

**Pass 2 — dense (MultiBit):**
1. `get_dense_entries_batch` fetches every candidate's dense entry in one batch read.
2. Take a `SCORING_GATE` permit again, then score each candidate with `MultiBitQuanDotProductEstimator` against the single whole-query dense embedding (symmetric with the document's whole-text dense vector), in parallel. Whole-document codes are encoded against the **zero centre** (`ZERO_CENTRE` = `u32::MAX`, `index_embedding_zero_centred`; design doc M2c), so `⟨q, c⟩ = 0` and **one** estimator serves every candidate. A dense code with any other `centre_id` is skipped, counted in `dense_corrupt_skipped` and ERROR-logged — never scored against a guessed centre. Measured before choosing it: zero vs nearest centre within ±0.001 nDCG at every cutoff @10–@100 on eight model-dataset pairs at 8 bits.
3. Build top-k min-heap and return sorted descending.

The `doc_filter` is applied **only in Pass 1**. Pass 2 operates on the already-filtered candidate list.

### Concurrency: the scoring gate (load-bearing)

`search()` runs its rayon work from a tokio task, and every search shares rayon's global pool. A rayon worker waiting inside a `join` steals **any** queued job, including another search's root job. The stolen search then runs on top of the waiting one's stack, so the first cannot return until the second finishes, and under steady load new root jobs keep arriving. Measured on FiQA at 32 concurrent clients before the fix: 19 of 32 connections stalled in Pass 1 for the entire 20 s run while the rest completed normally (p99 4–10 s across runs, max = the run length). The code before the hot-path work had the same flaw (p99 3–4 s, max 5–9 s under the same load); the faster Pass 1 made it worse, not new.

`SCORING_GATE` (`service/mod.rs`) is a process-wide tokio semaphore of `MAX_CONCURRENT_SCORING` = 2 permits around the two CPU sections. It bounds nesting to one level, and tokio admits waiters in FIFO order, so nothing starves. With it, FiQA at 32 clients went from p99 9.7 s / max 15.1 s to p99 308 ms / max 356 ms (p99 ≈ 1.2× p50, so what remains is queueing), and throughput rose from 110 to 125 qps. 2 permits beat 1, 4, 8 and no bound in a sweep. Concurrency is correct as well as fair: results at 32 clients are byte-identical to sequential ones.

Three rules keep it working:
- **Never hold a permit across an `.await`.** A search holding one permit while it waits for I/O and then for a second permit deadlocks at `MAX_CONCURRENT_SCORING` concurrent searches. `test_concurrent_searches_match_sequential_results` catches this.
- **Keep off-request-path work off the rayon pool.** The scan-result drop was `rayon::spawn`, and a 6 ms job on the rayon queue is stolen by workers waiting in some search's `join` exactly as a search is. Moving it to `spawn_blocking` alone cut the c=32 max from 20 s to 2.5 s. It is not free: a single client pays ~0.1 ms on SciFact and ~0.8 ms on FiQA (≈4%) against `rayon::spawn` with the gate, which keeps single-client latency but has 20–30% worse p99/max under load. A single dedicated dropper thread was worse on both counts (it falls behind at 64 clients).
- **The bound is process-wide because the pool is.** Other rayon users on a tokio thread (the RaBitQ quantisation in the embed path) are not gated, so a search can still nest one of those small jobs.
- **Keep the task floors (`MIN_ONE_BIT_ENTRIES_PER_TASK` / pass1 width, `MIN_CANDIDATES_PER_TASK`).** Every rayon task wakes a sleeping worker, and a woken worker yields up to 33 times before it sleeps again, so a search split into as many tasks as there are threads kept the pool spinning. Measured 2026-10-30 (engine bench, 16 clients, `get` + searches, per-thread `/proc/<pid>/task/*/schedstat`): 1.1 million rayon wake-ups a second (~2,300 per search, ~10 cores of spinning), and the threads serving `get` waited 32 µs for a core on every wake-up — `get` p99 1.03 ms against 0.02 ms alone. With the floors: 0.31 million a second, `get` p99 0.60 ms, search throughput +10%, p99 −14%, and single searches 2–15% faster at every width. The floor is divided by the Pass-1 width: a flat 4,096 left 4-bit searches too few tasks and cost them 4–6%. Most remaining wake-ups are `par_sort_unstable_by` in the grouping step. Shrinking the pool (`RAYON_NUM_THREADS=4`) gives a similar tail but slows large single searches, so it is not the fix.

## External dependency

**The embedding service must be running** for any vector insert or query to work. Without it, `semantic_search` calls will return an error. The service is not part of this workspace.

Requests use a **batch interface** (chunking happens in minnal, not the service). The service loads several models (the companion one: `gemma`, `qwen`), so **every request names the model** — `{model}` is `SemanticSearchConfig::model_name` (`[semantic_search] model`, lower-cased by the API config's `resolve`):
- `POST {base_url}/embedding/{model}/document` — body `{"payloads": [str, ...], "dimensions": N}` → `{"embeddings": [[f32], ...]}` (one vector per payload)
- `POST {base_url}/embedding/{model}/query` — same request/response shape
- `GET {base_url}/healthcheck` — `{"status", "models": {"<model>": {"status": "ok"|"loading"|"unreachable", ...}}}`; 503 while *any* model loads

A whole-text ("single") embedding is just a one-element `payloads` array (every query is one); a document sends its whole text plus one payload per sentence-window chunk. A model the service was not started with answers 404 `{"detail": "Unknown model ..."}`; non-2xx answers surface as `EmbeddingError::Status` with that detail. Default base URL: `http://localhost:8001`.

The service's API was single-model for a while (`/embedding/document`, model fixed server-side, `model_name` inert). It is multi-model again, so `model_name` is load-bearing: it routes every embed request **and** keys the query cache. Don't drop either.

### Startup probe and model checks

`check_embedding_service` checks `/healthcheck` lists `model_name` with status `ok` (`ModelNotServed` / `ModelNotReady` otherwise — it reads the model's own entry, not the HTTP status, because the service is 503 while *another* model loads; a body without `models` falls back to "2xx"), then embeds a fixed probe payload through **both** of that model's endpoints and validates the returned **dimension** against `embedding_dim`, then soft-warns if the probe vector is not unit-norm. The API server runs it at startup once per distinct (model, dimension) an existing semantic namespace uses (non-fatal), and again when a store is created or enables semantic search: `EmbeddingError::is_configuration_error` (not served, wrong dimension, 4xx) fails that request with 422; an unreachable or loading service only warns, since the embed queue retries.

**A namespace grows its own partition from one root posting (M3a).** When a namespace first enables semantic search, `SemanticSearchContext::init_namespace` writes one root posting (id 0) encoding against centre 0, the zero vector (`vector_kv::init_ivf`: WAL-backed puts, durable before the schema is saved; test `a_new_partition_survives_a_crash_right_after_it_is_written`). Postings past `2 · target_posting_size` chunks are split by the maintenance task (`ivf_split`, below). **No centroid file exists (M4):** the server checks a namespace's model only against the optional `supported_models` allow-list (`SemanticSearchContext::with_supported_models`; `UnsupportedEmbeddingModel` / `EmbeddingDimMismatch`) and otherwise relies on the enable-time probe of the service. Namespaces seeded from a file before M3 keep that partition (pre-M3 posting rows and `PostingOrigin::Seed` still decode) and simply start splitting; a rebuild moves them onto their own centres. `seed_ivf` is `#[cfg(test)]`: benches use it for static baselines (`MINNAL_BENCH_PARTITION=file`), nothing in production seeds. `for_namespace` loads a namespace's partition once into a registry of `PartitionHandle`s keyed by (name, `ns_id`), evicted on store drop and on a vector-index drop. A vector-index drop removes the partition and its journal with the data (`VECTOR_DATA_SUFFIXES` = `COMPANION_SUFFIXES`, one list, `companion_namespaces`): re-enabling starts from a root again.

**The partition is a `PartitionHandle` (M3a): current snapshot, routing epoch, maintenance lock.** A `NamespaceIvf` is an immutable snapshot (postings with state `Active` / `Draining` / `Retired`, parent, origin; centres append-only); `evolve` builds the next one and `publish` installs it. **Every vector write (route, encode, write, apply its delta) and every search (choose postings, scan them) runs inside the routing epoch (`read_epoch`); `publish` installs a snapshot and then waits until every write and search that entered before it has left, and `epoch_barrier` waits the same way.** That is what lets a split delete a posting's old keys without a search missing a chunk, or a write filing one under a posting that no longer takes chunks. **The epoch is a grace period, not a lock** (`layout.rs`, `Grace`): entering never waits, and a publish or barrier never holds up a write or search that starts after it. It was a fair tokio `RwLock`, so every publish and barrier (three per split) queued every new search and write behind the slowest one in flight; review 2026-10-17. `publish` is only called by maintenance under its lock, so the snapshot cannot change between `evolve` and the swap, and nothing is excluded while `evolve` runs. Guards: `a_new_reader_does_not_wait_behind_a_barrier`, `a_barrier_waits_for_readers_that_started_before_it`, `a_write_routed_before_a_publish_is_drained_with_the_rest` (fails if `publish` does not wait). The worker embeds *outside* the epoch (`embed_document_floats`), then routes and writes inside it against the snapshot current at that moment. Don't route outside the epoch or hold it across a network call. Tests: `a_search_during_a_split_misses_nothing`, `writes_racing_a_split_lose_nothing`.

**Splits go through a WAL-backed journal (`ivf_split`, `{ns}_ivf_journal`).** Plan → Prepare → Publish (record `Published` **before** the snapshot, then wait out older writes and searches) → Copy (per document under `lock_doc_vectors`: children into the meta, WAL, then the keys, `put_logged` to the vector index WAL; codes keep their `centre_id`) → Barrier (one `sync_vector_index_wal`; the same for the rebuild and reassignment barriers) → Delete → Retire. `recover` finishes `Published`/`Copied` splits and abandons `Planned` ones, re-reading the journal after each (a split it finishes runs its already-recorded reassignment, never a second one: `recovery_runs_a_recorded_reassignment_once`). **Recovery gates every use of a partition** (review 2026-10-17): a `PartitionHandle` starts with `needs_recovery`, and any maintenance error sets it again; `for_namespace` calls `ivf_split::ensure_recovered` before handing a partition out, and every maintenance entry point (`split_posting`, `maintain_partition_until`, `rebuild_partition`) calls `prepare` after taking the lock. Before, recovery ran only in the vector worker at startup, so an admin rebuild could run before it (drained a pending split's children, then recovery copied into retired postings: `a_rebuild_before_recovery_loses_nothing`), a failed recovery only logged, and an error mid-operation was retried in-process on top of its own unfinished record, reusing its ids (recovery at the next start then retired the retry's live postings: `a_failed_split_retried_in_process_survives_a_restart`). Guard for the gate: `a_partition_is_handed_out_only_after_its_journal_is_recovered`. **A drop stops maintenance first** (`DocStore::without_partition_maintenance` → `SemanticSearchContext::begin_drop`: refuse to hand out the namespace's partition, `mark_dropped` every loaded one, wait for each maintenance lock; `end_drop` after). Maintenance writes resolve namespaces with get-or-create, so a write after the removal recreated them (`a_drop_waits_for_running_maintenance_and_stops_it`); maintenance checks `is_dropped` after the lock and before every batch. **The drop also stops vector writes and reindexes** (2026-10-23): the vector worker resolves a namespace's partition once per pass, so after a drop it went on embedding the rest of the pass (56 embedding calls after the drop returned, in `a_drop_stops_the_worker_pass_on_its_store`), and `index_all` kept enqueuing from its own scan after the drop cleared the queue (`a_drop_during_a_reindex_leaves_no_queue_entries`). Now `begin_drop` waits out the routing epoch after `mark_dropped`, the worker checks `is_dropped` before the embedding call and again inside the epoch (embed and clear), `without_partition_maintenance` waits for the namespace's reindex claim (a reindex checks `is_dropping` after its claim and before each enqueue), the store drop clears the queue again after removing the primary namespace, and `request_maintenance` ignores a namespace being dropped. **A store drop closes its `WriteGate` first** (`DocStore::without_writes`, `store/types.rs`): every doc/KV write and reindex holds a guard, the drop refuses new ones and waits for those in progress; and every per-store data path resolves its namespace with `store_ns` (`AsyncDb::existing_namespace`, never get-or-create) — a `put` read the schema (removed last), then recreated the removed namespace (`writes_during_a_drop_leave_nothing_behind`). Field-index builds hold a guard too (moved into the build task; `add_index_inner`, `resume_pending_builds`, `reindex_all_until`) and stop at the next document once the store is being dropped (`a_drop_stops_a_running_index_build`). **An interrupted drop is finishable**: the cleanup skips a namespace already removed, and `open` runs `finish_interrupted_drops` first (a schema whose namespace is unregistered — only a drop leaves that) — before, a retry failed and the next open failed outright on the stale `ns_id` (`an_interrupted_drop_is_finished_by_a_retry_or_the_next_open`). **The queue clear is `vector_kv::clear_queue_for`**: prefix scan of the namespace's keys, `delete_no_wal` each, one `flush_namespaces` of the queue (durable before the drop goes on); WAL-backed deletes cost an fsync each — 48.5 s against 0.62 s for 20 000 entries on NVMe. **In the delete step the meta loses P before P's key is deleted** — the crash audit found the reverse order left a meta naming P with no key; this order is safe only because the redo deletes every key still under the draining P whether listed or not. Balanced 2-means is SPTAG's with the **mean** centres kept (the one deviation from SPFresh; `cluster::split`), on `rabitq::reconstruct_single_bit` reconstructions, on the blocking pool. Tests: `a_split_survives_a_crash_before_any_write` (crash before every write × four flush patterns), `postings_split_by_themselves_as_a_namespace_grows`. **Measure split cost with the background workers running** (`vector_bench` calls `enable_all_workers`): `AsyncDb::open_with_config` starts none, and without LSM compaction every split's flush leaves its L0 files for good — FiQA indexing read 300–370 s instead of 36 s, which was first blamed on the journal's WAL fsyncs. A no-WAL, flush-batched journal was built and measured on that wrong premise: 35.5 s against 35.7 s, so it was reverted.

**Reassignment and merges (M3b) use the same journal; split and merge share one drain path.** `maintain_partition` (the only entry point; the maintenance task and the bench call it) repeats: split oversized postings, each followed by its **reassignment** (`ivf_split/reassign.rs`, LIRE step 5: the two halves plus the `reassign_range` active postings nearest the old centre; candidates by LIRE's two conditions on the code reconstructions, moved to their nearest active posting), then **merge** postings at or under `merge_limit` (`ivf_split/merge.rs`: first of the 64 nearest with `chunks(S)+chunks(Q) < split_limit`; the smaller is drained into the larger). A split and a merge both *drain* a posting (`drain_copy`/`drain_delete`, a `DrainRule` decides each chunk's destination); a merge sends a chunk nearer its old centre than to the kept one to its nearest active posting instead. Rules: (1) the reassignment's record is written **before** the split's record is deleted, so a crash between them still reassigns; (2) a reassignment's source stays active, so its key **shrinks with a WAL-backed put** (or delete), never no-WAL — a lost shrink would leave a duplicate and a wrong meta count for good; (3) a source gives up a chunk **only if its destination key holds it** (`matched`, counting duplicates), which makes a redo safe even if a copy did not land; (4) **`epoch_barrier` before any original goes** — a search that began before a copy could scan the destination early and the source late; (5) counts move by **meta** changes only, because the count table loads from the meta (deriving a delta from the key would double-count after a crash between the meta and key writes). (7) **reassignment's cost is the move decision, not I/O**: a profile of FiQA indexing (988 splits) put 172 of 241 s of maintenance in deciding which scope chunks move (every chunk of the halves and 64 neighbouring postings, checked against a few centres), 32 s in reading the scope, and about 10 s in all the WAL writes together. Now: a live run decides once and shrinks the entries it copied from (a redo from `Copied` decides again); LIRE's conditions are decided **without reconstructing the code** (`Scorer`: with `x̂ = c + s·σ`, `D(x̂,t) − ‖x̂‖² = ‖t‖² − 2⟨c,t⟩ − 2s⟨σ,t⟩`, `⟨σ,t⟩` from per-byte lookup tables (`SignDot`), `⟨c,t⟩` cached per centre pair) and only a candidate is reconstructed to find its nearest posting; the scope is read with one `scan_prefixes_batch`. FiQA indexing 245 s → 55 s (M3a, split only: ~35 s), same splits and moves as before (the scorer accumulates in f64). `the_scorer_decides_as_the_reconstruction_does` pins it against the reconstruction (`decide_reconstructed`, test-only), on stored and random codes, with and without the gate. Keep a guard's lock out of a `match` scrutinee in `Scorer` — that deadlocked the first version. (8) **per-document moves run in batches of `BATCH_DOCS` = 16, one batch at a time** (`in_batches`, polled in the calling task, never spawned, so the thread-local crash point still stops every later write): each batch takes its documents' locks with `vector_kv::lock_docs_vectors` (stripes deduplicated and taken in ascending order; never take a document's lock again while holding them), reads source keys, metas and destination keys with `get_multiple`, then writes per document, meta first. A document with chunks in several sources is one item (moves combined; sources share one used-copy mask per destination via `matched_with`; one meta write). **Keep batches narrow and sequential — they are foreground tail latency.** A batch holds its documents' locks for about `BATCH_DOCS` WAL meta writes (~2.3 ms each here), and every upsert or delete of a document on one of those stripes waits for it, as does every WAL write behind its fsyncs. M3b ran 4 lanes of 64 (FiQA indexing 55 s → 47.5 s), which with 256 stripes held about every stripe at once: in the M5 investigation (2026-10-11) a delete-and-insert load while partitions split put delete p50/p99/max at 37/582/1434 ms. With `DOC_VECTOR_LOCK_STRIPES` = 4096 and 16 documents one batch at a time: 43/109/166 ms, and more inserts got through (3,745 against 3,076 in the same 60 s). No `futures` crate: it is not a dependency. (6) **a split whose smaller half is at or under `merge_limit` is refused** (marked unsplittable at that size): the merge dissolves the half and routes its chunks, nearer their own old centre, back into the big half, over the limit again — on SciFact 2-means isolated 3 outliers of a 262-chunk posting and splits and merges alternated ~900 times per maintenance pass, 85 s per batch (`a_split_that_the_next_merge_would_undo_is_refused`) — **a deviation from SPTAG**, whose `Split` has no such check: SPTAG merges lazily (a search probing a posting of ≤ 10 vectors queues an async merge), so the same cycle only advances per query; minnal merges eagerly, so it needs the guard. Recorded with the evidence in the design doc, *Why a split can be refused*. `skip_uncertain_moves` requires each comparison to win by more than `2 · error_bound · ‖A − B‖` (`nearer`). Merges are woken by `PartitionHandle::needs_maintenance` (limits set by `for_namespace`) from every path that applies a delta. Counters: `PartitionHandle::counters` → `maintenance` in `GET /admin/indices/{ns}/vector/partition` and the bench's *chunk moves per inserted chunk*. Tests: `reassign_and_merge_survive_a_crash_before_any_write`, `writes_racing_reassign_and_merge_lose_nothing`, `a_search_during_reassign_and_merge_misses_nothing`, `reassign_moves_chunks_to_a_nearer_posting`, `postings_merge_by_themselves_as_documents_are_deleted`.

**A rebuild (M4, `ivf_split/rebuild.rs`) is one journal operation that drains every active posting at once.** `POST /admin/indices/{ns}/vector/rebuild` → `DocStore::start_vector_rebuild` (202; `VecRebuildInProgress` 409 while one runs; status in `SemanticSearchContext::rebuild_status`, shown as `rebuild` in the partition endpoint) → `rebuild_partition`, under the maintenance lock: read every active posting's codes (`postings_entries`), k-means on their reconstructions (`cluster/kmeans.rs`, the simulation's procedure: k-means++ on a 50k sample, 20 Lloyd iterations, K = active postings by default), record `Op::Rebuild { first_centre, first_posting, postings, drained }` (`Planned`), append the centres and new postings (`PostingOrigin::Rebuild`), mark every old one `Draining`, publish, `drain_copy` each old posting with `DrainRule::Nearest` (the nearest new posting), barrier, `Copied`, epoch barrier, `drain_delete` each, retire them in one publish, delete the record; then the ordinary `maintain_partition` splits what k-means left oversized. Recovery abandons `Planned` (`abandon` handles every kind: new postings retired empty, drained ones active again) and redoes `Published`/`Copied` (`rebuild::finish`). Rules: (1) **k-means runs on its own rayon pool** of `rebuild_threads` (1 or 2, hard cap `MAX_REBUILD_THREADS` = 2 by user decision), built inside `spawn_blocking` — never the global pool, where a search waiting in a `join` would steal a long job (the scoring-gate rule); (2) **k-means streams over the codes** (`kmeans(n, dim, point, …)` asks for point `i` into a buffer), so memory is the codes, not every chunk as floats (FiQA: ~20 MB instead of ~530 MB); means are summed in point order, so a seed gives the same centres on any pool; (3) a centre no chunk is nearest is dropped before the record (no empty posting); (4) rebuild moves are counted apart (`rebuild_moves`), so `chunk_moves()` stays the ongoing maintenance cost the bench reports per inserted chunk. Measured: SciFact 7 s, FiQA 151 s on 2 threads (k-means ~60 s of it at 2.8 s per iteration; FiQA-size seeding 6 s). No automatic trigger, and centre drift is not a signal for one: a rebuild re-encodes nothing, so it *raises* drift (every code becomes foreign; SciFact and FiQA mean 0.28–0.40 → 0.45–0.51). What it can change is how much of a full read's results a search finds within its budget, which the recall check measures (FR-007, `ivf_split/recall_check.rs`, `GET /admin/indices/{ns}/vector/recall-check`): run it, rebuild, run it again with the same seed. Its queries are real ones' embeddings sampled from `system_qemb_cache` (`vector_kv::sample_cached_query_embeddings`, one bounded page from a seeded start) and, with fewer than 20 cached, stored chunks' 1-bit reconstructions; it needs no embedding service either way. **Keep real queries first:** across the eight M4 gate runs real-query overlap@10 at a 1% read rose 1.8–5.4 points with a rebuild against gate recall gains of 1.1–4.4, while chunk queries did not move on FiQA gemma drifting (0.805 → 0.804, gate +3.2) and overstated FiQA qwen shuffled (+4.0, gate +1.1). Compare a check before and after, not against a fixed bar: the level differs by dataset (1% read: 0.56–0.63 SciFact, 0.85–0.91 FiQA). The reference full read is capped at `MAX_REFERENCE_ENTRIES` (500k) because `search()` holds every scanned entry in memory until it returns. Every recall check, `?codes=true` read and rebuild is recorded in the TTL namespace `system_partition_history` (`ivf_split/history.rs`, TTL `[semantic_search] partition_history_ttl_secs`, default 30 days; WAL-backed puts) and read back by `GET /admin/indices/{ns}/vector/history` (with `ttl_secs`); nothing is collected in the background. The recall check loads settings with `load_vector_settings`, so it works on KV stores too (it used the doc-store schema loader at first and failed on KV). `GET /admin/indices/vector/settings` (`DocStore::vector_server_settings`) exposes the server-wide `[semantic_search]` values for minnal_ui's Vector Index Ops tab. Tests: `a_rebuild_fits_postings_to_the_chunks_they_hold`, `a_rebuild_survives_a_crash_before_any_write` (fails with the barrier removed), `writes_racing_a_rebuild_lose_nothing`, `a_search_during_a_rebuild_misses_nothing`, `a_rebuild_runs_in_the_background_without_the_embedding_service` (doc store; counts embedding requests). We use our own k-means, not a crate: `kmeans` needs nightly, `clustering` is unseeded with farthest-point seeding, and `linfa-clustering` brings ~10 crates and needs every point as floats in memory (user decision, 2026-10-11).

**Crash tests only prove something if the simulated crash loses no-WAL data.** Until 2026-10-11 `AsyncDb::crash()` let every `KVStore`'s `Drop` flush its memtable, so no-WAL writes always survived and none of the vector crash tests (M0-2 audit, M3a split, M3b) could fail for a missing barrier flush — deleting the split's barrier left its crash test green. `KVStore` now skips that flush once its database is marked crashed (`a_simulated_crash_loses_unflushed_no_wal_writes`). Mutation-check a crash test: remove the guard it is for and confirm it fails.

**Codes decode through their own `centre_id`, never the posting they are filed under.** `VectorIndex` carries `cluster_id` (the posting, its key prefix) and `centre_id` (what it was encoded against). `search()` builds a centre's Pass-1 estimators on first use (`CentreEstimators`, a table indexed by centre id, one `OnceLock` per id) and looks each chunk up by its `centre_id` (caching the last lookup per entry); building them for every centre made each query's cost grow with every centre the namespace ever had (`a_search_builds_estimators_only_for_the_centres_its_codes_use`). Whole-document codes depend on no centre at all (zero centre, M2c). That is what lets M3 move postings and change centres without re-encoding dense codes. **Centres are never collected — known limitation, deliberately deferred (user decision 2026-10-17, design doc decision 14; filed as FR-008).** A moved code keeps its `centre_id`, so a split's and a rebuild's moved chunks still use the old centres; a centre is unused only once every code encoded against it is deleted or re-embedded, rare outside heavy churn. Costs no longer grow with the count (lazy estimators; `NamespaceIvf` keeps centres in a `CentreSet` of `Arc`s rotated once, so `evolve` is ~2 ms at 1,957 or 10,000 centres, was 9.5 / 26 ms), so what remains is ~6 KB of memory per centre. If it is built, do it at the end of a rebuild and mind the risks recorded in the design doc (*Known limitation: centres are never collected*): never delete a centre of a non-retired posting or one a code still uses (scan afresh after the final publish, under the maintenance lock) — getting it wrong makes chunks silently unscorable; let retired postings name a missing centre or the partition fails to load; never reuse a deleted id. Indexing and search are generic over `IvfLayout` (`cluster/layout.rs`): `NamespaceIvf` (routing postings, posting → centre, centres with the namespace's seed) in production, and `ClusterIndex` as the identity layout for tests, benches and raw `vector_kv` users. Tests: `codes_are_scored_against_their_own_centre_not_their_posting`, `a_dense_code_not_encoded_against_the_zero_centre_is_skipped_and_counted`, `index_embeddings_encodes_the_dense_vector_against_the_zero_centre`. Do not reintroduce a server-wide centroid file: when there was one (one `cluster_path` beside a separate `model` key, later one file per model), both bundled sets were 768-dim, so pairing a model with the other model's centroids loaded without error and skewed the partition (`release.sh` once hard-coded qwen under a gemma config and a FiQA query read 92% of its index), and a general-purpose set collapsed specialist text (SciFact: 43% of documents in one cluster).

## Configuration: server vs namespace

The server's `[semantic_search]` holds only what is about the embedding service (unknown keys are rejected, so a leftover namespace key, or the removed `centroid_dir`, fails startup):

```toml
[semantic_search]
embedding_service_url = "http://localhost:8001"
# query_embedding_cache_ttl_secs, embedding_request_timeout_secs, embedding_connect_timeout_secs
# [[semantic_search.supported_models]] name/dimension — optional allow-list; empty: any model the service serves
# [semantic_search.maintenance] (schema defaults, plus engine-only threads and rebuild_threads)
```

Everything that shapes one namespace's index lives in its schema's `vector_index` (`doc_store/vector_settings.rs`, design doc M2a): `embedding_model` (default gemma) and `embedding_dim` (768), `chunking.window_size` / `sliding_size` (4 / 2), `quantisation.pass1_bits` / `pass2_bits` (1 / 8, read-only), `quantisation.pass2_centre` (`"zero"`, read-only; future Pass-2 widths stay within 4–8 bits, where the zero centre was measured to hold), `search.min_probes` / `max_probes` / `first_pass_top_k` / `top_k` (1 / 256 / 1000 / 100). Defaults are written into the schema when semantic search is first enabled; model, dimension and chunking are **fixed for the namespace's life** (kept across a vector-index drop); search settings change via the `UpdateVectorSearch` amendment and per request. The library's `SemanticSearchConfig` is still the per-call bundle `search()` / `index_embeddings` take; the doc store builds it per namespace (`SemanticSearchContext::for_namespace`), and raw `vector_kv` users build it themselves.

> **`window_size` / `sliding_size` shape the stored document chunks**, which is why they are fixed once a namespace has settings: a change would leave already-indexed documents with the old chunks, silently. They do **not** affect queries (queries are not chunked), so the query-embedding cache needs no clear. **Don't reintroduce query chunking** without re-running the BEIR harness: word-window query chunks were measured worse and far costlier than the whole-query vector, and sentence windows gained nothing (`report/query-embedding-report.md`).

## Key types

- `VectorIndex` — a quantised embedding entry: holds `cluster_id` (the posting it is filed under), `centre_id` (the centre it was encoded against, which decodes it), packed bit codes (`packed_vector`), scalar correction coefficients (`addition_factor`, `scaling_factor`, `error_bound`), and `quantisation_style` (`SingleBit` or `MultiBit { number_of_bits }`).
- `VectorKvStore` — trait over the storage backend: `scan_sparse_clusters_batch` (every SingleBit entry of the probed postings, one call) and `get_dense_entries_batch` (MultiBit bytes per candidate), which `search()` uses, plus their single-item forms `scan_sparse_cluster` / `get_dense_entry`.
- `Cluster` — a single centroid + its pre-computed norms for fast distance estimation.
- `ClusterIndex` — a fixed set of centroids with its rotation: the identity layout (posting = centre = cluster) for tests, benches and raw `vector_kv` users. Namespaces use `NamespaceIvf` instead.
- `SemanticSearchConfig` — all tunable parameters for the search pipeline.
