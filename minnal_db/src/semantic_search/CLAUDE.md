# semantic_search — Vector Quantisation + ANN Search

Implements IVF (Inverted File Index) clustering with RaBitQ quantisation for two-pass approximate nearest-neighbour search over dense embeddings. Vectors are stored in `minnal_db`; this crate handles quantisation, cluster assignment, and search.

## How it works

### Chunking (done here, not by the service)

The embedding service no longer chunks text — `src/chunking/mod.rs` does. **Only documents are chunked**: `chunk_document` splits on **sentence** boundaries and groups the sentences into overlapping **sliding windows** (`window_size` sentences per window, advancing `sliding_size`; the last window keeps the remainder), each joined into one payload string. **Queries are not chunked** — one whole-query embedding serves both passes (see *Search* below). The service receives a list of already-prepared payloads and returns one embedding per payload.

### Indexing (dual quantisation)

Each document goes through a **single** embedding service call (`embed_document`) that embeds one ordered payload list — `[whole_text, chunk₀, chunk₁, …]` — and splits the (order-preserving) response by position:

1. **MultiBit (dense)** — `payload[0]`, one embedding for the whole document text, quantised to `number_of_bits_for_dense_quantisation` bits per dimension. Stored in `{ns}_dense_vector` keyed by `doc_id`. Used for high-precision re-ranking in Pass 2.
2. **SingleBit (sparse, sliding-window)** — `payload[1..]`, `chunk_document`'s N sliding-window chunks → N embeddings. Each chunk is independently assigned to its nearest IVF cluster and quantised to 1 bit per dimension. Stored in `{ns}_sparse_vector` under composite keys `[cluster_id (4B BE) ‖ doc_id]`. Used for fast first-pass cluster scans.

Folding both into one call is one round trip and one GPU batch of `N+1` (the service preserves payload order, so position 0 is always the dense vector). The query path (`embed_query`) sends a single payload: the whole query.

A third namespace, `{ns}_sparse_vector_meta`, is each document's index record: `text_hash (8B) ‖ count (2B) ‖ cluster_ids`. The cluster list is the only way delete and upsert cleanup find the document's chunk keys again; the text hash (`vector_kv::text_hash`, FNV-1a, pinned by `text_hash_is_stable`) records which text the vectors came from. It is written for every indexed document, including one with no chunks.

**Durability split (no-WAL payloads, WAL-backed meta and deletes).** The vector **payloads** — `{ns}_sparse_vector` and `{ns}_dense_vector` — are written with `put_no_wal` (`vector_kv::upsert_vectors`): they are bulky and reconstructable by re-embedding, so a per-chunk WAL fsync plus a second copy in the WAL is pure overhead. A crash before the memtable flush can drop a just-indexed vector (or flush one half and lose the other); that window is healed by the queue (M0-1 below) and by vector-index reconciliation, which treats a doc as indexed only when **both** the sparse-meta and dense halves are present **and the meta's text hash matches the document's current text** (`has_complete_vector_index`).

**The meta is WAL-backed and written between the stale deletes and the new keys — do not move it.** `upsert_vectors` goes: (1) delete stale cluster keys (WAL), (2) put the new meta (WAL, durable on return), (3) put the chunk keys and the dense entry (no-WAL). The meta must list every key that can be on disk at every moment, and each namespace's memtable flushes on its own schedule (size-triggered), so a no-WAL meta could be lost while a key written after it was flushed: a later delete then misses the key for good, and a reused document id inherits it. One fsync per document upsert, negligible beside the embedding call. Crash-audit test: `delete_racing_a_reembed_survives_a_crash_anywhere`.

**The meta's text hash catches stale vectors.** A document write and its embed enqueue are separate writes; a crash between them saves the new text with no queue entry while the old vectors stay. Reconciliation computes each document's current embedding text, and a hash mismatch reads as not indexed, so it re-embeds. This is why reconciliation has **no count short-circuit any more**: it skipped namespaces whose meta/dense counts covered their keys, and stale vectors change no count. Measured cost of the full pass: 1.44 s for 57,600 entries (`reconcile_cost_on_a_fiqa_sized_store`), once per start, in the background. Crash-audit test: `reembed_survives_a_crash_anywhere`; unit test: `test_reconcile_reembeds_vectors_of_stale_text`.

**Deletes stay WAL-backed.** The cleanup **deletes** stay **WAL-backed** — the stale-cluster deletes on upsert and the full reverse-lookup `delete_vector` (reads `{ns}_sparse_vector_meta` to delete every composite key, then the dense entry). They are tiny key-only tombstones, and unlike a lost write a lost delete is *not* self-healing: reconciliation re-enqueues only docs *missing* an index, whereas a lost delete leaves an *orphan* composite key a re-embed never revisits.

**A queue entry is completed only after its vectors are durable — do not complete first.** The vector writes above are no-WAL, but the stale-key deletes and the queue completion (`complete_entry`, a `merge`) are WAL-backed and durable at once. Completing before a flush let a crash keep the completion and the deletes while losing the new vectors: a re-embedded document kept its *old* meta and dense entry, which `has_complete_vector_index` accepts, so nothing re-enqueued it (stale vectors for good, minus its moved chunks). The worker now writes (`upsert_vectors`), collects up to `COMPLETION_BATCH` (256) written entries, flushes their vector namespaces once (`vector_kv::make_vector_writes_durable` → `AsyncDb::flush_namespaces`), and only then completes them (`complete_embed`); a failed flush completes nothing. `finish_embed` is the same three steps for one entry. The flush is unconditional, not gated on the no-WAL flag, because the flag is cleared *before* a concurrent flush finishes. Regression tests: `crash_before_reembed_is_flushed_keeps_new_vectors` (fails without the flush), `a_failed_flush_completes_nothing`, `crash_after_flush_before_completion_redoes_the_entry`.

**One document's vector writes are serialised (`vector_kv::lock_doc_vectors`).** `upsert_vectors` and `delete_vector` are multi-key read-modify-writes whose only index of the sparse keys is the cluster list in `{ns}_sparse_vector_meta`, and they run concurrently whenever a document delete races the vector worker. Interleaved, a delete read the old list and then deleted the list the upsert had just written, leaving the upsert's new cluster keys orphaned for good (measured 260 in 300 racing rounds). Both now hold a striped per-`(namespace, doc)` async lock across their whole body; the process owns the database exclusively (directory lock), so in-process locking is enough. Don't call one from inside the other while holding it. Regression test: `racing_upsert_and_delete_leave_no_orphaned_cluster_keys`.

**Reconciliation must not overwrite live queue work, and the worker drops vectors of a vanished document.** Reconciliation decides from a snapshot while writes continue, so it re-reads each document and enqueues with `vector_kv::enqueue_embed_if_absent` (atomic insert-if-absent), never the overwriting `enqueue_embed`: an overwrite replaced newer text with the snapshot's (stale vectors for good) or replaced a delete's `Clear` tombstone with an embed (a deleted document back in search). And `complete_embed` checks the source document still exists and removes the vectors if not — an entry written from a snapshot can land after the tombstone was processed. That check runs **before** the completion: after it, a crash between the two kept the completion and the vectors with nothing left to remove them (crash-audit test `embedding_a_vanished_document_survives_a_crash_anywhere`). Regression tests: `enqueue_if_absent_never_overwrites_a_newer_entry_or_a_tombstone`, `embedding_a_deleted_document_leaves_no_vectors`.

**Startup reconciliation runs after the worker's first pass over the crash queue (`VecIndexWorkerHandle::startup_pass`).** A delete cut short by a crash leaves the document, no vectors, and a `Clear` tombstone. Reconciliation never overwrites a tombstone, so run concurrently it skipped the document and the tombstone's removal then left it unindexed until the next restart. Signalled after the first *pass*, not an empty queue, so a steady stream of new writes cannot hold reconciliation off. Test: `startup_reconciliation_runs_after_the_crash_queue_is_processed` (fails 4 runs in 5 without the wait).

**An interrupted vector-index drop is finished at open (`DocStore::finish_interrupted_vector_index_drops`).** Dropping saves the schema with semantic search off, then clears the queue and removes the vector namespaces in the background; a crash in between left both, and the worker would process the leftover entries and recreate the namespaces. At open, before any worker starts, every namespace with vector data or queue entries but no semantic-search schema gets `drop_vector_index_data`. Test: `an_interrupted_vector_index_drop_is_finished_at_open`.

**Reindex records report progress; they do not block.** A `vector_reindex.json` record used to stay `"running"` for good (nothing ever wrote `"complete"`), so every later `reindex-all` was refused with 409. Now concurrency is an in-memory claim per namespace held only while `index_all` / `kv_index_all` enqueues (`ReindexClaim`), and `vec_reindex_progress` (async) brings a `"running"` record up to date as it reads it: `"complete"` once `enqueue_done` and none of the namespace's work is queued, `"failed"` if the enqueue never finished and no claim is held (a crash cut it short). Tests: `a_finished_reindex_does_not_block_the_next`, `a_reindex_interrupted_by_a_crash_does_not_block_the_next`.

**Crash audit (design doc M0-2).** `vector_kv::crash_audit_tests` runs each write path with a simulated crash before every write (`crash_point!()`, a test-only countdown before each vector-index write in `vector_kv`), under five flush patterns (no namespace, each one alone, all), then restarts in production's order (worker pass, reconciliation, worker pass) and checks that the vector index matches what the store holds. Add a `crash_point!()` before any new vector-index write, and a scenario for any new multi-step path.

The **query-embedding cache** (`system_qemb_cache`, below) follows the same split. Populates are no-WAL (`put_no_wal`): the cache is TTL-bounded and fully regenerable from the embedding service, so a dropped populate is just a future miss, and staying off the WAL removes a per-populate fsync from the query hot path. The admin clear (`DELETE /admin/indices/vector/query-cache`) deletes **WAL-backed**: the periodic no-WAL flush tick has usually already persisted the entries being cleared, so a no-WAL tombstone lost to a crash before the next tick would resurrect them — serving entries the operator explicitly cleared until the TTL expires. The clear is a rare admin operation, so the per-delete fsync is off the query path.

### Rotation (codes live in a rotated space)

Each namespace has its own rotation: the seed is recorded in its schema (`vector_index.quantisation.rotation_seed`, read-only, default `DEFAULT_ROTATION_SEED`) and its `NamespaceIvf` rotates its centres and queries with it. A `ClusterIndex` holds one `FhtKacRotator` and a rotated copy of every centroid. Indexing (`index_embedding_rotated`) picks the nearest cluster on the **original** vector, then quantises `Pᵀx` against `Pᵀc`; `search()` rotates each query once and uses the rotated query for every term that meets a code (the query sum, `scaled_query_sum`, and the packed dot products), while cluster probing and `⟨q, c⟩` use the original (rotation preserves both). **Mixing the two spaces is the bug to watch for**: a rotated code scored with an unrotated query sum, or the reverse. `rotated_scoring_matches_scoring_fully_rotated_inputs` checks the formula wiring, and `rotated_index_finds_the_source_document_end_to_end` (with a first-pass cut of 3, so Pass 1 must rank correctly too) fails if either pass's query is left unrotated. Dimensions that are odd or below 8 get no rotation (only tiny test indexes); the API rejects such an `embedding_dim`. Its effect depends on how evenly a model's residuals spread over dimensions. Gemma (already even): estimator RMSE −0.6% / −2.2% (SciFact / FiQA), nothing else changes. Qwen (concentrated): without rotation the 1-bit estimate is biased (−0.0105 / −0.0035); rotation removes that, cuts RMSE 11–15% and adds 1.2–1.4 points of Pass-1 recall. nDCG@10 and latency are unchanged on both (design doc M1, `report/rabitq-rotation-audit.md`).

### Search (two-pass ANN)

`embed_query` makes **one** embedding of the whole query (one payload, one service call) and uses it for **both** passes: as Pass 2's dense vector and as Pass 1's single MaxSim query vector (`QueryEmbeddings { sparse: vec![dense.clone()], dense }`). Queries used to be split into 4-word sliding windows; a BEIR evaluation (`report/query-embedding-report.md`) found the whole-query vector never worse and often better. With a tight first-pass cut it kept more relevant docs (ArguAna candidate recall 0.991 vs 0.870). It is also far cheaper: one embedding instead of 1+N, and `n_probes` clusters instead of the union over every fragment (up to 74% faster search). Document-style sentence windows for long queries gained nothing either, so there is **no query-chunking option**. `search()` still accepts several Pass-1 query vectors (general MaxSim) and returns empty if either input is empty. The embedding is cached in the `system_qemb_cache` TTL namespace, keyed by `model ‖ 0x00 ‖ dim (u32 BE) ‖ query text` (`vector_kv::query_cache_key`; `query_embedding_cache_ttl_secs`, default 1 day). Model and dimension are in the key because each namespace picks its own and one service serves several models: keyed by text alone, namespaces with different models (or the same model at two dimensions) would share query vectors. Since queries are not chunked, chunking settings never invalidate it either; clear it (`DELETE /admin/indices/vector/query-cache`) only if the service changes what it serves under the same model name.

**Pass 1 — sparse (SingleBit), ColBERT MaxSim over document chunks:**
1. Use the Pass-1 query vector (the whole-query embedding; fetched from the `system_qemb_cache` TTL namespace on a hit).
2. Find its nearest clusters by Euclidean distance, walking them nearest first until their entry counts reach `probe_budget_entries`, bounded by `min_probes` / `max_probes` (`cluster::select_probes`, design doc M2d; per query vector, then the union). Entry and chunk counts live in a `CountTable` shared by every snapshot of a namespace's partition: counted at load from the document records (`{ns}_sparse_vector_meta`, which since M3a record each posting's chunk count; read a page at a time), then kept current by the `PostingDelta` every vector write returns (`(posting, chunks)` per entry written or deleted). They are **exact** as far as the meta goes: nothing writes a namespace's vectors before its partition is loaded (every writer goes through `for_namespace`), and the split executor applies its own deltas. The split trigger depends on it. `ClusterIndex` has no counts (`posting_entries` = `None`, counted as 0), so raw `vector_kv` users, tests and the criterion benches use `ProbeSettings::fixed(n)` (exactly n probes, the old behaviour). This is an **exact, exhaustive** scan — `ClusterIndex::find_top_n_cluster_ids_batch` computes the distance to *every* centroid (over a contiguous centroid matrix) and selects the `n_probes` nearest (`select_nth_unstable`, ~O(C)). There is **no neighbour graph / approximate traversal**: coarse-assignment cost is **T·C·D** (query vectors × centroids × dim), and production `T = 1`, so it is ~microseconds at C≈256. A graph is the wrong lever — approximate on the most recall-sensitive stage, marginal at a few hundred nodes. The contiguous-matrix scan was a measured ~12% win back when queries were chunked (T up to 100); **parallelising the per-vector scans was tried and reverted (~2.4× slower — the work is microseconds, so the thread pool costs more than it saves)**; a blocked GEMM is the only remaining lever and only pays at far larger C. See `report/Semantic-Search-Architecture.md`.
3. `scan_sparse_clusters_batch(probe_clusters)` fetches every probed cluster in **one** call: `LSMTree::scan_prefixes` reads each LSM layer once for the whole prefix set (L1 seeks per prefix via the sparse index), then the value log resolves each pointer with its own `pread`. This scan is most of a warm query's cost and scales with the number of entries probed.
4. Take a `SCORING_GATE` permit (see *Concurrency* below).
   Then build one `SingleBitQuanDotProductEstimator` per (probed cluster, query vector). Each query vector's sum is computed **once** (`query_sum`) and passed to `with_query_sum`; recomputing it per cluster was 2.9 ms of a 6.0 ms search at 40 query vectors, because this pre-pass is single-threaded (it was not when estimators were built inside the old per-cluster fold).
5. Flatten every probed entry into one list and score it **in parallel over entries, not clusters** (IVF clusters are skewed; one can hold a third of a corpus), each entry into its own row of a flat `n_query`-wide matrix. Entries are read zero-copy from their rkyv archive. The optional `doc_filter` (RoaringBitmap predicate) skips non-matching docs here, as do corrupt or wrong-style entries.
6. Group per document with **ColBERT MaxSim**: sort the kept entry indices by `doc_id`, and fold each run of one document's entries (a document's chunks can sit in several probed clusters) with an element-wise max. `S(q, d) = Σ_i max_j ⟨q_i, d_j⟩`; with production's single whole-query vector this is `max_j ⟨q, d_j⟩`, the document's best-matching chunk. The sort replaced a per-document `HashMap` whose allocations and cross-thread merge were half of a FiQA query.
7. Keep the top `first_pass_sparse_search_top_k` with `select_nth_unstable` — O(n), because Pass 2 re-ranks and does not care about their order.
8. Release the permit and hand the scanned entries to `spawn_blocking` to be freed (~90k heap buffers on FiQA, ~6 ms single-threaded) off the request path.

**Pass 2 — dense (MultiBit):**
1. `get_dense_entries_batch` fetches every candidate's dense entry in one batch read.
2. Take a `SCORING_GATE` permit again, then score each candidate with `MultiBitQuanDotProductEstimator` against the single whole-query dense embedding (symmetric with the document's whole-text dense vector), in parallel. Whole-document codes are encoded against the **zero centre** (`ZERO_CENTRE` = `u32::MAX`, `index_embedding_zero_centred`; design doc M2c), so `⟨q, c⟩ = 0` and **one** estimator serves every candidate. A dense code with any other `centre_id` is skipped, counted in `dense_corrupt_skipped` and ERROR-logged — never scored against a guessed centre. Measured before choosing it: zero vs nearest centre within ±0.001 nDCG at every cutoff @10–@100 on eight model-dataset pairs at 8 bits.
3. Build top-k min-heap and return sorted descending.

The `doc_filter` is applied **only in Pass 1**. Pass 2 operates on the already-filtered candidate list.

### Concurrency: the scoring gate (load-bearing)

`search()` runs its rayon work from a tokio task, and every search shares rayon's global pool. A rayon worker waiting inside a `join` steals **any** queued job, including another search's root job. The stolen search then runs on top of the waiting one's stack, so the first cannot return until the second finishes, and under steady load new root jobs keep arriving. Measured on FiQA at 32 concurrent clients before the fix: 19 of 32 connections stalled in Pass 1 for the entire 20 s run while the rest completed normally (p99 4–10 s across runs, max = the run length). The code before the hot-path work had the same flaw (p99 3–4 s, max 5–9 s under the same load); the faster Pass 1 made it worse, not new.

`SCORING_GATE` (`service/mod.rs`) is a process-wide tokio semaphore of `MAX_CONCURRENT_SCORING` = 2 permits around the two CPU sections. It bounds nesting to one level, and tokio admits waiters in FIFO order, so nothing starves. With it, FiQA at 32 clients went from p99 9.7 s / max 15.1 s to p99 308 ms / max 356 ms (p99 ≈ 1.2× p50, so what remains is queueing), and throughput rose from 110 to 125 qps. 2 permits beat 1, 4, 8 and no bound in a sweep. Concurrency is correct as well as fair: results at 32 clients are byte-identical to sequential ones.

Three rules keep it working:
- **Never hold a permit across an `.await`.** A search holding one permit while it waits for I/O and then for a second permit deadlocks at `MAX_CONCURRENT_SCORING` concurrent searches. `test_concurrent_searches_match_sequential_results` catches this.
- **Keep off-request-path work off the rayon pool.** The scan-result drop was `rayon::spawn`, and a 6 ms job on the rayon queue is stolen by workers waiting in some search's `join` exactly as a search is. Moving it to `spawn_blocking` alone cut the c=32 max from 20 s to 2.5 s. It is not free: a single client pays ~0.1 ms on SciFact and ~0.8 ms on FiQA (≈4%) against `rayon::spawn` with the gate, which keeps single-client latency but has 20–30% worse p99/max under load. A single dedicated dropper thread was worse on both counts (it falls behind at 64 clients).
- **The bound is process-wide because the pool is.** Other rayon users on a tokio thread (the RaBitQ quantisation in the embed path) are not gated, so a search can still nest one of those small jobs.

## External dependency

**The embedding service must be running** for any vector insert or query to work. Without it, `semantic_search` calls will return an error. The service is not part of this workspace.

Requests use a **batch interface** (chunking happens in minnal, not the service). The service loads several models (the companion one: `gemma`, `qwen`), so **every request names the model** — `{model}` is `SemanticSearchConfig::model_name` (`[semantic_search] model`, lower-cased by the API config's `resolve`):
- `POST {base_url}/embedding/{model}/document` — body `{"payloads": [str, ...], "dimensions": N}` → `{"embeddings": [[f32], ...]}` (one vector per payload)
- `POST {base_url}/embedding/{model}/query` — same request/response shape
- `GET {base_url}/healthcheck` — `{"status", "models": {"<model>": {"status": "ok"|"loading"|"unreachable", ...}}}`; 503 while *any* model loads

A whole-text ("single") embedding is just a one-element `payloads` array (every query is one); a document sends its whole text plus one payload per sentence-window chunk. A model the service was not started with answers 404 `{"detail": "Unknown model ..."}`; non-2xx answers surface as `EmbeddingError::Status` with that detail. Default base URL: `http://localhost:8001`.

The service's API was single-model for a while (`/embedding/document`, model fixed server-side, `model_name` inert). It is multi-model again, so `model_name` is load-bearing: it routes every embed request **and** keys the query cache. Don't drop either.

### Startup probe and model checks

`check_embedding_service` checks `/healthcheck` lists `model_name` with status `ok` (`ModelNotServed` / `ModelNotReady` otherwise — it reads the model's own entry, not the HTTP status, because the service is 503 while *another* model loads; a body without `models` falls back to "2xx"), then embeds a fixed probe payload through **both** of that model's endpoints and validates the returned **dimension** against `embedding_dim`, then soft-warns if the probe vector is not unit-norm. The API server runs it at startup once per distinct (model, dimension) an existing semantic namespace uses (non-fatal), and again when a store is created or enables semantic search: `EmbeddingError::is_configuration_error` (not served, wrong dimension, 4xx) fails that request with 422; an unreachable or loading service only warns, since the embed queue retries.

**A namespace grows its own partition from one root posting (M3a).** When a namespace first enables semantic search, `SemanticSearchContext::init_namespace` writes one root posting (id 0) encoding against centre 0, the zero vector (`vector_kv::init_ivf`: no-WAL then flushed, durable before the schema is saved). Postings past `2 · target_posting_size` chunks are split by the maintenance task (`ivf_split`, below). Centroid files are no longer copied; the server still loads one `ClusterIndex` per model from `{centroid_dir}/{model}/clusters.json` to check a namespace's model and dimension (`UnsupportedEmbeddingModel` / `EmbeddingDimMismatch`) until M4 removes them. Namespaces seeded from a file before M3 keep that partition (pre-M3 posting rows still decode) and simply start splitting. `for_namespace` loads a namespace's partition once into a registry of `PartitionHandle`s keyed by (name, `ns_id`), evicted on store drop and on a vector-index drop. A vector-index drop removes the partition and its journal with the data (`VECTOR_DATA_SUFFIXES` = `COMPANION_SUFFIXES`, one list, `companion_namespaces`): re-enabling starts from a root again.

**The partition is a `PartitionHandle` (M3a): current snapshot, routing epoch, maintenance lock.** A `NamespaceIvf` is an immutable snapshot (postings with state `Active` / `Draining` / `Retired`, parent, origin; centres append-only); `evolve` builds the next one and `publish` installs it. **Every vector write (route, encode, write, apply its delta) and every search (choose postings, scan them) holds the routing epoch's read guard; publishing takes the write guard.** That is what lets a split delete a posting's old keys without a search missing a chunk, or a write filing one under a posting that no longer takes chunks. The worker embeds *outside* the epoch (`embed_document_floats`), then routes and writes inside it against the snapshot current at that moment. Don't route outside the epoch or hold it across a network call. Tests: `a_search_during_a_split_misses_nothing`, `writes_racing_a_split_lose_nothing`.

**Splits go through a WAL-backed journal (`ivf_split`, `{ns}_ivf_journal`).** Plan → Prepare → Publish (record `Published` **before** the snapshot, under the write guard) → Copy (per document under `lock_doc_vectors`: children into the meta, WAL, then the keys, no-WAL; codes keep their `centre_id`) → Barrier (flush sparse + meta) → Delete → Retire. `recover` (run by the vector worker before its first pass, `doc_store::ivf_maintenance::recover_all`) finishes `Published`/`Copied` splits and abandons `Planned` ones. **In the delete step the meta loses P before P's key is deleted** — the crash audit found the reverse order left a meta naming P with no key; this order is safe only because the redo deletes every key still under the draining P whether listed or not. Balanced 2-means is SPTAG's with the **mean** centres kept (the one deviation from SPFresh; `cluster::split`), on `rabitq::reconstruct_single_bit` reconstructions, on the blocking pool. Tests: `a_split_survives_a_crash_before_any_write` (crash before every write × four flush patterns), `postings_split_by_themselves_as_a_namespace_grows`.

**Codes decode through their own `centre_id`, never the posting they are filed under.** `VectorIndex` carries `cluster_id` (the posting, its key prefix) and `centre_id` (what it was encoded against). `search()` builds Pass-1 estimators for every centre of the layout and looks each chunk up by its `centre_id` (caching the last lookup per entry). Whole-document codes depend on no centre at all (zero centre, M2c). That is what lets M3 move postings and change centres without re-encoding dense codes. Indexing and search are generic over `IvfLayout` (`cluster/layout.rs`): `NamespaceIvf` (routing postings, posting → centre, centres with the namespace's seed) in production, and `ClusterIndex` as the identity layout for tests, benches and raw `vector_kv` users. Tests: `codes_are_scored_against_their_own_centre_not_their_posting`, `a_dense_code_not_encoded_against_the_zero_centre_is_skipped_and_counted`, `index_embeddings_encodes_the_dense_vector_against_the_zero_centre`; `a_namespace_never_reads_the_servers_centroid_files`. This replaced a single `cluster_path` beside a separate `model` key: both bundled sets are 768-dim, so pairing a model with the other model's centroids loaded without error and skewed the IVF partition (`release.sh` once hard-coded qwen under a gemma config and a FiQA query read 92% of its index). Do not reintroduce a centroid-file setting independent of the model.

## Cluster centroids

Pre-built centroids ship per model at `service/embedding_support/{model}/clusters.json` — currently **gemma** and **qwen** (the two models the companion embedding service serves), each 256 centroids × 768 dims. A namespace uses the set for its `vector_index.embedding_model` (see above). Each file is ~4.4 MB of JSONL — do not read it; it is data, not code.

**The gemma set was regenerated on 2026-09-25 for the PyTorch embedding service.** The earlier ONNX/FastEmbed service mean-pooled raw hidden states and skipped EmbeddingGemma's two Dense projections, so its vectors, and the old centroids fit on them, lived in a different space (cosine ≈ 0 vs the real embeddings). Any vector index built with the old service is incompatible with this file: re-index it (`POST /admin/indices/{ns}/vector/reindex-all`) and clear the query-embedding cache (`DELETE /admin/indices/vector/query-cache`). Provenance, reproducible with the embedding service's `generate_sample_embeddings.sh` + `generate_cluster_centroids.sh`: ELI5 QA pairs (first 25,024 records, `question + "\n" + answer`, document prompt), K-means k=256, seed 42. It is a **general-purpose example set**: well spread on general text (253/256 clusters used by held-out ELI5), but specialist text collapses (SciFact: 43% of docs in one cluster), so domain-specific deployments should fit centroids on their own data.

## Configuration: server vs namespace

The server's `[semantic_search]` holds only what is about the embedding service and the centroids (unknown keys are rejected, so a leftover namespace key fails startup):

```toml
[semantic_search]
embedding_service_url = "http://localhost:8001"
centroid_dir = "service/embedding_support"   # {centroid_dir}/{model}/clusters.json
# query_embedding_cache_ttl_secs, embedding_request_timeout_secs, embedding_connect_timeout_secs
# [[semantic_search.supported_models]] name/dimension — optional; restricts and checks the loaded sets
```

Everything that shapes one namespace's index lives in its schema's `vector_index` (`doc_store/vector_settings.rs`, design doc M2a): `embedding_model` (default gemma) and `embedding_dim` (768), `chunking.window_size` / `sliding_size` (4 / 2), `quantisation.pass1_bits` / `pass2_bits` (1 / 8, read-only), `quantisation.pass2_centre` (`"zero"`, read-only; future Pass-2 widths stay within 4–8 bits, where the zero centre was measured to hold), `search.probe_budget_entries` / `min_probes` / `max_probes` / `first_pass_top_k` / `top_k` (70,000 / 1 / 1024 / 1000 / 100). Defaults are written into the schema when semantic search is first enabled; model, dimension and chunking are **fixed for the namespace's life** (kept across a vector-index drop); search settings change via the `UpdateVectorSearch` amendment and per request. The library's `SemanticSearchConfig` is still the per-call bundle `search()` / `index_embeddings` take; the doc store builds it per namespace (`SemanticSearchContext::for_namespace`), and raw `vector_kv` users build it themselves.

> **`window_size` / `sliding_size` shape the stored document chunks**, which is why they are fixed once a namespace has settings: a change would leave already-indexed documents with the old chunks, silently. They do **not** affect queries (queries are not chunked), so the query-embedding cache needs no clear. **Don't reintroduce query chunking** without re-running the BEIR harness: word-window query chunks were measured worse and far costlier than the whole-query vector, and sentence windows gained nothing (`report/query-embedding-report.md`).

## Key types

- `VectorIndex` — a quantised embedding entry: holds `cluster_id`, packed bit codes (`binary_quantised_vector`), scalar correction coefficients (`addition_factor`, `scaling_factor`, `error_bound`), and `quantisation_style` (`SingleBit` or `MultiBit { number_of_bits }`).
- `VectorKvStore` — trait over the storage backend; exposes `scan_sparse_cluster(cluster_id)` (returns all SingleBit entries for that cluster) and `get_dense_entry(doc_id_bytes)` (returns the MultiBit bytes for a document).
- `Cluster` — a single centroid + its pre-computed norms for fast distance estimation.
- `ClusterIndex` — one model's centroids, loaded per model from `{centroid_dir}/{model}/clusters.json` at startup.
- `SemanticSearchConfig` — all tunable parameters for the search pipeline.
